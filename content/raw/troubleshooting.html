> Purpose: when something "does not connect", find the layer that is broken in under two minutes — interface/route, DNS, TCP, HTTP, or the proxy in between — instead of re-running the exploit. ## Isolate the layer | Test | Layer | A healthy result | | --- | --- | --- | | ip a, ip route, ping | L3 | an address, a default route, replies | | dig, getent hosts | DNS | the expected IP | | nc -nv IP PORT | L4 | succeeded / open | | ss -tlnp | local stack | your listener bound | | curl -v | L7 | headers, status code | | tcpdump | ground truth | SYN, SYN-ACK, or nothing | Work down the list. The first failing row is the problem. ## A. Connectivity and routing ### Step 01 — Check the local stack and route Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ip a; ip route; ping -c 3 ip route get ``` Look for: an address on the correct interface, a default route, and ICMP replies.
Decision: no reply but the route exists → ICMP may be filtered; continue to Step 03 (TCP). Wrong interface/route → fix VPN/routing before anything else.
Next: Step 02.
Common mistake: treating a failed ping as "host down". Many exam targets drop ICMP while serving TCP perfectly.
Evidence: the ip a/ip route output and the ping result. ### Step 02 — Check DNS Priority: Core · Run on: Kali · Status: Syntax Checked ```bash cat /etc/resolv.conf dig +short getent hosts ``` Look for: the intended resolver, the expected A record, and getent agreeing with dig.
Decision: dig works but an application fails → the app uses /etc/hosts or a different resolver. Add the entry explicitly.
Next: Step 03.
Common mistake: debugging DNS when you should use the IP. If the record is wrong, put the mapping in /etc/hosts and move on.
Evidence: the resolver config and the resolved address. ## B. Ports and listeners ### Step 03 — Raw TCP probe Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nc -nv # scriptable nc -z -v && echo OPEN || echo CLOSED ``` Look for: succeeded / open, or a banner.
Decision: open but the exploit fails → the service is there; the problem is protocol/credentials. Closed/timeout → firewall or wrong port.
Next: Step 04 (if you expect a listener) or Step 05 (HTTP).
Common mistake: testing through proxychains when the tool uses UDP, or forgetting that -z sends no payload and some services log it.
Evidence: the probe result. ### Step 04 — See what is listening locally Priority: Core · Run on: target or Kali · Status: Syntax Checked ```bash ss -tlnp ss -tulpn ``` Look for: the port bound to 0.0.0.0 vs 127.0.0.1.
Decision: bound to 127.0.0.1 → only local processes can reach it; tunnel in (Tunneling page). Not listening → the service is down.
Next: Step 05 or the pivot.
Common mistake: starting a listener on 127.0.0.1 and expecting a remote callback. Bind 0.0.0.0 or the correct interface.
Evidence: the ss line for the port. ## C. Application layer ### Step 05 — Verbose HTTP Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -v http://:/ curl -vk https://:/ curl -v --resolve :: https://:/ ``` Look for: Connected to …, the request line, response headers, and the status code.
Decision: HTTP works but the browser/app does not → vhost or Host header. TLS handshake fails → -k or SNI (use --resolve).
Next: the HTTP or Directory & VHost page.
Common mistake: reading only the body. -v shows the redirect, the auth challenge, and the exact header causing the failure.
Evidence: the -v transcript. ## D. Ground truth ### Step 06 — Capture traffic Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash sudo tcpdump -i -nn -A port sudo tcpdump -i -nn -w host ``` Look for: whether packets leave, and whether anything returns.
Decision: SYN out, nothing back → filtered/routed wrong. SYN, RST → port closed. SYN, SYN-ACK, then RST → TLS/app mismatch. Nothing at all → wrong interface.
Next: fix the layer the capture proves is broken.
Common mistake: capturing on eth0 while the traffic uses tun0. Confirm with ip route get .
Evidence: the pcap file, or the filtered output showing the handshake. ### Step 07 — Read the failure correctly Priority: Core · Run on: Kali · Status: Syntax Checked | Capture / probe result | Meaning | Next | | --- | --- | --- | | SYN sent, no reply | Filtered, or wrong route | ip route get, try the pivot | | SYN → RST | Closed | Wrong port / service down | | SYN → SYN-ACK → RST | App or TLS mismatch | curl -v, -k, SNI | | Connection open, no data | Protocol mismatch | Try the right client | | Works locally, fails remotely | Bound to 127.0.0.1 | Rebind / tunnel | | Works from pivot, not Kali | Routing between Kali and pivot | Check the tunnel | Common mistake: jumping to the exploit when the handshake already shows the port is closed. Read the four packets first. ## E. Proxy and pivot checks ### Step 08 — Verify the path through a proxy Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash proxychains4 -q curl -v http:/// proxychains4 -q nc -nv nmap -Pn -sT -p ``` Look for: responses that only appear when the proxy is in use.
Decision: curl fails but nc works → application issue, not routing. Both fail → the pivot cannot reach the target; test from the pivot itself.
Next: fix the tunnel (Tunneling & Pivoting).
Common mistake: using -sS or ICMP through a SOCKS proxy. Use -sT -Pn.
Evidence: the proxied transcript. ### Step 09 — Systematic checklist Priority: Core · Run on: Kali · Status: Syntax Checked 1. ip a — am I on the right network? 2. ip route get — which interface will it use? 3. getent hosts — does the name resolve to the IP I expect? 4. nc -nv — is the port actually open? 5. ss -tlnp — is my listener bound where I think? 6. curl -v — what does the application say? 7. tcpdump — what actually crosses the wire? 8. Only then revisit the exploit. Rule: never change the exploit until one of these eight tests has failed. Guessing wastes more time than measuring. ## F. Decision tree | Symptom | Start at | Do not | | --- | --- | --- | | Nothing responds at all | Step 01 | Reinstall the tool | | Name does not resolve | Step 02 | Hard-code and forget the cause | | Port "closed" | Step 03 | Assume the host is down | | Callback never arrives | Step 04 | Regenerate the payload | | HTTP 400/404/redirect | Step 05 | Blame the exploit | | Works locally, fails remotely | Step 04 (bind address) | Add firewall rules blindly | | Only through a proxy | Step 08 | Use a SYN scan | | Everything looks fine | Step 06 (capture) | Keep retrying | ## G. Evidence to preserve - The failing command and its full output. - The layer that was actually broken, and the test that proved it. - Any routing or /etc/hosts change you made (so you can undo it). - The pcap if the failure was intermittent. ## H.
