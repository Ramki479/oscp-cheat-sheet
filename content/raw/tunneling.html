> Purpose: reach a host your Kali cannot route to — by making a host you already control carry the traffic. Pick the smallest tunnel that answers the question, and know which side listens. ## Which tunnel? | Situation | Use | Listens on | | --- | --- | --- | | One port on the pivot's [localhost](http://localhost) | ssh -L (Step 01) | Kali | | Expose a Kali service to the target network | ssh -R (Step 02) | pivot / target | | Many ports, many hosts | SOCKS: ssh -D or chisel (Steps 03-06) | Kali | | Whole subnet, no per-tool flags | sshuttle (Step 10) | Kali (needs root) | | No SSH, quick single relay | socat (Step 08) | Kali | | Windows pivot, no extra binaries | netsh portproxy (Step 09) | Windows pivot | Two questions before any tunnel: what does the pivot reach that Kali does not? and which direction is the connection allowed? Most failures are a listener bound to 127.0.0.1 when the client connects from outside. ## A. SSH tunnels ### Step 01 — Local port forward (ssh -L) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh -L :127.0.0.1: @ # example: reach the pivot's local MySQL on Kali:3306 ssh -L 3306:127.0.0.1:3306 @ ``` Look for: a normal SSH session; while it stays open, 127.0.0.1: on Kali reaches as seen from the pivot.
Decision: the service is on another internal host → point the middle at that host: ssh -L :: @.
Next: connect to 127.0.0.1: on Kali.
Common mistake: assuming the forward reaches Kali's network. The right-hand side is resolved from the pivot, not from Kali.
Evidence: the SSH session plus a successful connection to the forwarded port. ### Step 02 — Remote port forward (ssh -R) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh -R :127.0.0.1: @ # example: make Kali's HTTP server reachable on the target network ssh -R 8080:127.0.0.1:8000 @ ``` Look for: traffic to : arriving at Kali's 127.0.0.1:.
Decision: internal hosts must reach your payload server → this is the pattern (serve from Kali, forward onto the pivot).
Next: start the Kali service first, then open the tunnel.
Common mistake: GatewayPorts no (the default) binds the remote listener to 127.0.0.1 on the pivot — only the pivot itself can use it. Add -R 0.0.0.0::… only if the server allows it.
Evidence: a curl from the pivot to 127.0.0.1:. ### Step 03 — Dynamic SOCKS (ssh -D) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh -D 1080 -N -f @ ``` Look for: a SOCKS proxy on 127.0.0.1:1080 that exits at the pivot.
Decision: more than one port or host to reach → SOCKS. One port → ssh -L is simpler.
Next: Step 04 (proxychains).
Common mistake: forgetting -N -f: without them you get an interactive shell and no background proxy.
Evidence: ss -tlnp | grep 1080 on Kali. ### Step 04 — Proxychains Priority: Core · Run on: Kali · Status: Syntax Checked ```bash echo 'socks5 127.0.0.1 1080' | sudo tee -a /etc/proxychains4.conf proxychains4 nmap -Pn -sT -p 445,3389 proxychains4 nxc smb -u -p ``` Look for: the tool's output arriving through the proxy, and |S-chain|-<>- lines when -q is not set.
Decision: DNS fails inside the proxy → enable proxy_dns in the config, or use IP addresses only.
Next: run the actual enumeration tool through it.
Common mistake: using a SYN scan (-sS) through proxychains. A SOCKS proxy carries TCP connect only — use -sT, and -Pn because ICMP is not proxied.
Evidence: the proxychains command and its successful output. ## B. Chisel (no SSH required) ### Step 05 — Start the chisel server Priority: Core · Run on: Kali · Status: Syntax Checked ```bash chisel server -p --reverse --socks5 ``` Look for: server: Listening on https://0.0.0.0:.
Decision: the pivot can reach Kali outbound → this is the most reliable pivot when SSH is closed.
Next: Step 06.
Common mistake: running the server without --reverse and then trying an R: client connection — reverse tunnels are rejected.
Evidence: the server log showing a client connection. ### Step 06 — chisel client (reverse SOCKS) Priority: Core · Run on: pivot/target · Status: Syntax Checked ```bash # upload chisel to the pivot first, then chisel client : R:socks ``` Look for: client: Connected and a SOCKS proxy on Kali at 127.0.0.1:1080.
Decision: need a single port instead of SOCKS → chisel client : R::127.0.0.1:.
Next: point proxychains at 1080 (Step 04).
Common mistake: assuming the SOCKS port is configurable on the client in R:socks form — chisel uses 1080 by default; specify R:1081:socks to change it.
Evidence: the client log and a proxied request. ## C. Without SSH ### Step 07 — socat relay Priority: Conditional · Run on: Kali or pivot · Status: Syntax Checked ```bash socat TCP-LISTEN:,fork TCP:: # bind to all interfaces so other hosts can use it socat TCP-LISTEN:,fork,bind=0.0.0.0 TCP:: ``` Look for: connections to being relayed to :.
Decision: need many ports → SOCKS. Need one port and no SSH/chisel → socat.
Next: connect to the relay.
Common mistake: omitting fork — socat then handles exactly one connection and exits.
Evidence: a successful connection through the relay. ### Step 08 — Windows portproxy Priority: Conditional · Run on: Windows pivot · Status: Syntax Checked ```shen netsh interface portproxy add v4tov4 listenport= listenaddress=0.0.0.0 connectport= connectaddress= netsh interface portproxy show all netsh advfirewall firewall add rule name="portproxy" dir=in action=allow protocol=TCP localport= ``` Look for: the rule listed by show all, and the port reachable from Kali.
Decision: you have admin on a Windows host that reaches the internal subnet → portproxy, no binaries needed.
Next: connect to :.
Common mistake: adding the portproxy but not the firewall rule, then concluding it does not work. Both are required.
Evidence: show all output and a successful connection. ### Step 09 — sshuttle Priority: Conditional · Run on: Kali · Status: Documented ```bash sshuttle -r @ /24 # typical: route the internal subnet sshuttle -r @ 10.10.10.0/24 ``` Look for: c : Connected to server and direct tool usage with no proxychains prefix.
Decision: you have SSH and root on Kali, and want transparent routing for every tool → sshuttle. No root or no SSH → SOCKS.
Next: run tools normally against the routed subnet.
Common mistake: passing the pivot's own /24 instead of the internal subnet you need. Also: sshuttle needs Python on the pivot.
Evidence: a successful direct connection to an internal host. ## D. Chains and verification ### Step 10 — Double pivot Priority: Advanced · Run on: Kali · Status: Documented ```bash # SSH jump host, then SOCKS that exits at the second pivot ssh -D 1080 -J @ @ # or chain a second chisel hop through the first SOCKS ``` Look for: 127.0.0.1:1080 now exiting inside the second network.
Decision: each additional hop adds latency and failure points — only add one when the target is genuinely unreachable from the first pivot.
Next: re-run Step 04 against the new exit.
Common mistake: stacking proxychains on proxychains. One SOCKS entry that already exits deep enough is cleaner than two.
Evidence: the hop chain and a request that only succeeds through it. ### Step 11 — Prove the tunnel works Priority: Core · Run on: Kali · Status: Syntax Checked ```bash proxychains4 -q curl -s -o /dev/null -w "%{http_code}\n" http:/// proxychains4 -q nxc smb -u -p ``` Look for: a real status code or a valid SMB response — not a timeout.
Decision: timeout → the pivot cannot reach the target, or the listener is bound to 127.0.0.1. Test from the pivot itself first.
Next: enumerate the internal host.
Evidence: the successful proxied request. ## E. Decision tree | Situation | Do this | Do not | | --- | --- | --- | | One service on the pivot | ssh -L (Step 01) | Build a SOCKS proxy | | Need Kali reachable from inside | ssh -R (Step 02) | Bind to 127.0.0.1 and expect others to use it | | Many ports/hosts | ssh -D • proxychains (Steps 03-04) | Add a forward per port | | SSH closed, outbound allowed | chisel (Steps 05-06) | Give up on pivoting | | Windows pivot, admin | netsh portproxy (Step 08) | Upload a Linux binary | | Need whole-subnet routing | sshuttle (Step 09) | Prefix every tool manually | | One port, no tooling | socat (Step 07) | Write a custom relay | | Tunnel "connects" but tools time out | Reachability or bind address | Blame the tool | ## F. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | connection refused on the listener | Service bound to 127.0.0.1 | Rebind to 0.0.0.0 or use -L | | proxychains: connection timed out | SOCKS not running / wrong port | Check ss -tlnp, fix the config | | nmap finds nothing through proxy | SYN scan / ICMP | -sT -Pn | | DNS fails through proxy | UDP not proxied | proxy_dns, or use IPs | | -R listener only local to pivot | GatewayPorts no | Use chisel or 0.0.0.0: if permitted | | chisel R: rejected | Server lacks --reverse | Restart with the flag | | sshuttle exits immediately | No root / no python on pivot | Run with sudo, or use SOCKS | | netsh rule works locally only | Firewall rule missing | Add the inbound rule | ## G. Evidence to preserve - The tunnel command on both ends (server and client). - Proof of reachability from the pivot (curl, nc -vz) and through the tunnel from Kali. - The proxy config line you added, and the exact proxied command. - Which host is the pivot, and which network it opened. ## H.
