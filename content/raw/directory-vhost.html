> Purpose: find what a web server hides — directories and files on a host you already know, and other hostnames served by the same IP. These are different questions with different tools; mixing them wastes the most time of any enumeration step. ## Two different questions
Question Technique Signal Tools
What paths exist on this host? path fuzzing: http://IP/FUZZ different status/size per path ffuf, gobuster dir, feroxbuster
Which hostnames does this IP serve? Host: FUZZ. header response differs from the default vhost ffuf, gobuster vhost
Which names exist in DNS? resolve FUZZ. an A record appears gobuster dns, dnsx, ffuf
Subdomain vs vhost. DNS enumeration asks the resolver, "does this name exist?" Vhost enumeration asks the web server, "do you serve a different site for this Host: header?" A name can be a working vhost with no DNS record, and a DNS name can point at a server that only shows its default page. On the exam, always run both when you see a domain. ## A. Setup and baseline ### Step 01 — Pick a wordlist Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ls /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt ls /usr/share/seclists/Discovery/Web-Content/raft-small-words.txt ls /usr/share/wordlists/dirb/common.txt ``` Look for: the expected line counts (raft-medium-directories ≈ 30k, raft-small-words ≈ 43k, dirb common ≈ 4.6k).
Decision: first pass → dirb/common.txt (fast). Solid pass → raft-medium-directories.txt. Vhosts → raft-small-words.txt or a subdomain list.
Next: Step 02.
Common mistake: starting a 30k-word scan before a 4.6k one. The first pass finds the obvious app; the big list is for when it does not.
Evidence: the wordlist path and line count. ### Step 02 — Baseline the server Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -sI http:/// curl -s http:///robots.txt curl -s -o /dev/null -w "%{http_code} %{size_download}\n" http:///thisdoesnotexist- ``` Look for: server header, redirects, robots.txt entries, and the 404 size — the number you will filter on.
Decision: a 404 returns a custom page with a stable size → add -fs . A wildcard returns 200 for everything → Step 15.
Next: Step 03.
Common mistake: skipping the baseline and then filtering by status code alone. Custom 404 pages commonly return 200.
Evidence: the 404 status and size. ## B. Directory enumeration ### Step 03 — ffuf (fast, flexible) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:///FUZZ -w -mc 200,204,301,302,307,401,403 -ac ``` Look for: hits with a size different from the baseline, and 301 redirects that reveal a directory.
Decision: a directory appears → re-run with FUZZ inside it (-u http:///found/FUZZ). A file appears → fetch it. Nothing → Step 04 with a bigger list.
Next: Step 06 for extensions, Step 09 for authenticated paths.
Common mistake: leaving -ac off a wildcard server — every word becomes a hit and the output is useless.
Evidence: the ffuf output with the matched sizes. ### Step 04 — gobuster dir Priority: Core · Run on: Kali · Status: Syntax Checked ```bash gobuster dir -u http:// -w -x php,txt,html -t 30 ``` Look for: Status: 200 [Size: ...] lines and Found redirects.
Decision: gobuster is faster and quieter than ffuf for a plain directory pass; keep it for the first sweep, ffuf for filtering tricks.
Next: Step 06.
Common mistake: forgetting -x — without extensions you miss index.php, config.txt, backup.html.
Evidence: the gobuster summary and hits. ### Step 05 — feroxbuster (recursive, resumable) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash feroxbuster -u http:// -w -x php,html,txt -o ``` Look for: a tree of found directories, automatically recursed, and a written report at .
Decision: a deep app (many nested dirs) → feroxbuster saves the most time. Shallow app → gobuster is enough.
Next: review the output file for 200/301 entries.
Common mistake: letting recursion run unbounded on a large app. Add --depth 2 and -t 30 to stay in control.
Evidence: the contents. ### Step 06 — Extensions and recursion Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:///FUZZ -w -e .php,.txt,.html,.bak -t 40 ffuf -u http:///FUZZ -w -recursion -recursion-depth 2 gobuster dir -u http:// -w -x php,aspx,jsp,html,txt feroxbuster -u http:// -w --depth 2 -x php,html ``` Look for: source backups (.bak, .old, ~), config files (.env, .git/HEAD), and admin panels.
Decision: the stack is known (PHP, [ASP.NET](http://ASP.NET), Java) → match the extension list to it instead of guessing all.
Next: Step 07 if the output is noisy.
Common mistake: adding extensions to every word, which multiplies requests by the number of extensions. Use a file-oriented list instead.
Evidence: the hits per extension. ### Step 06a — HTTPS with a self-signed certificate Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash gobuster dir -k -u https:// -w -x php,txt,html ffuf -u https:///FUZZ -w -k -ac feroxbuster -u https:// -w -k ``` Look for: the same hits over TLS that you saw over HTTP.
Decision: TLS fails entirely → the service may use SNI (Step 16) or a non-standard port; confirm with curl -k first.
Next: Step 07.
Common mistake: letting the scanner abort on certificate errors. Labs almost always use self-signed certificates — -k is the normal case, not an exception.
Evidence: the HTTPS hit list. ### Step 07 — Remove false positives Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:///FUZZ -w -fs ffuf -u http:///FUZZ -w -fc 404,429 gobuster dir -u http:// -w -b "" ``` Look for: a short, readable hit list.
Decision: many identical sizes → filter by size (-fs). Many different 404s → filter by code. gobuster hides 404 by default; -b "" shows every code.
Next: triage with the table in Section D.
Common mistake: filtering too aggressively and hiding the real hit. Always keep one unfiltered run for comparison.
Evidence: the filter used and the resulting hits. ### Step 08 — -mc all and the 403/500 problem Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:///FUZZ -w -mc all -ac ffuf -u http:///FUZZ -w -mc all -fs ``` What it actually does: ffuf's default matcher is 200-299,301,302,307,401,403,405,500 — 403 and 500 already appear by default. -mc all does not "unhide" them; it adds the codes outside that list (300, 304, 400, 402, 406, 409, 418, 429, 503…).
When it matters: the app answers 429 when it rate-limits you (a WAF telling you it noticed), 503 when a backend is down but the path exists, or 304 on conditional requests. Those are invisible without -mc all.
For 403/500 specifically: the fix is not the status code, it is the baseline. Compare -fs against a known-missing path, or filter the false-positive class with -fc 403,500 and inspect what remains.
Next: Section D for 403 bypass attempts.
Common mistake: adding -mc all and drowning in 10,000 hits. Pair it with -ac or a size filter, every time.
Evidence: the exact matcher/filter used. ### Step 09 — Authenticated and header-based fuzzing Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:///FUZZ -w -b "SESSION=" -ac ffuf -u http:///FUZZ -w -H "Authorization: Bearer " -ac ``` Look for: paths that only exist for a logged-in user — admin panels, API routes, user data.
Decision: you have a cookie → always re-run the discovery pass authenticated. The unauthenticated result is only half the map.
Next: Step 10 for parameters.
Common mistake: forgetting that the cookie value expires mid-scan; re-login and restart, or the whole run is noise.
Evidence: the authenticated hit list. ### Step 10 — Parameter and POST fuzzing Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash ffuf -u "http:///login.php?FUZZ=test" -w -fs ffuf -u http:///login.php -X POST -d "username=admin&password=FUZZ" -w -fc 200 ``` Look for: a parameter name that changes the response, or a login that returns a different status/length on success.
Decision: a hidden parameter appears → test it for injection. A login differential appears → brute force with the Passwords page.
Next: the relevant vulnerability page.
Common mistake: assuming a 302 is failure. -fc 200 filters the failure page when failure returns 200 — verify both directions first.
Evidence: the request and the differing response. ### Step 11 — API and JSON endpoints Priority: Conditional · Run on: Kali · Status: Documented ```bash ffuf -u http:///api/FUZZ -w -mc all -ac ffuf -u http:///api/FUZZ -w -X POST -H "Content-Type: application/json" -d '{}' -mc all -ac ``` Look for: 200 with JSON, 401/403 on real routes, 405 meaning the route exists but needs another method.
Decision: 405 → re-run with -X POST/-X PUT. 401 → the route exists; find a token.
Next: inspect the schema, then test the parameters.
Common mistake: treating 404 JSON as "no API". Many frameworks return 404 with a JSON body for unknown routes — compare bodies, not just codes.
Evidence: the routes and their responses. ## C. Virtual host and subdomain enumeration ### Step 12 — Virtual hosts with ffuf Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -s -o /dev/null -w "%{size_download}\n" -H "Host: doesnotexist." http:/// ffuf -u http:/// -H "Host: FUZZ." -w -fs ``` Look for: hosts whose response size differs from the default vhost.
Decision: a hit → add to /etc/hosts and browse that hostname directly. No hits → Step 14 (DNS names may still exist).
Next: enumerate the new host from Step 03.
Common mistake: omitting -fs. A default vhost answers every Host header with 200 and a fixed size; without the filter you get 43,000 "hits".
Evidence: the baseline size and the differing hosts. ### Step 13 — Virtual hosts with gobuster Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash gobuster vhost -u http:// -w --append-domain ``` Look for: Found: dev. Status: 200 [Size: ...].
Decision: gobuster auto-filters the baseline wildcard, which makes it the quicker first vhost pass; confirm hits with Step 12.
Next: browse the found host.
Common mistake: pointing -u at an IP while using --append-domain — the Host header becomes word. and nothing matches. Use the domain.
Evidence: the found vhosts and their sizes. ### Step 14 — DNS subdomain enumeration Priority: Core · Run on: Kali · Status: Syntax Checked ```bash gobuster dns -d -w -r ffuf -u http://FUZZ./ -w -fc 404 ``` Look for: names that resolve, and names that resolve and serve content.
Decision: a name resolves → add it to /etc/hosts, then run Step 03 against it. A name resolves but shows the default page → still note it; it may be a different app on another port.
Next: re-run directory enumeration per host.
Common mistake: using an internet resolver for an internal domain (-r 8.8.8.8). Point -r at the internal DNS server (often the DC).
Evidence: the resolved names and their IPs. ### Step 15 — Wildcards (DNS and vhost) Priority: Core · Run on: Kali · Status: Syntax Checked ```bash dig +short anything. @ curl -s -o /dev/null -w "%{http_code} %{size_download}\n" -H "Host: anything." http:/// ``` Look for: a wildcard A record, or a fixed-size 200 for any Host.
Decision: wildcard DNS → filter known IPs; wildcard vhost → always filter by size. Note the wildcard in your report — it explains why brute force "found" thousands of hosts.
Next: Step 12 with the measured size.
Common mistake: reporting the wildcard as a discovery. It is a server configuration, not a host.
Evidence: the wildcard response and the filter that neutralised it. ### Step 16 — HTTPS and SNI vhosts Priority: Conditional · Run on: Kali · Status: Documented ```bash ffuf -u https:/// -H "Host: FUZZ." -w -k -fs curl -k --resolve :443: https:/// ``` Look for: a certificate or page that differs per hostname.
Decision: the vhost is selected by SNI, not the Host header → use --resolve with curl, or ffuf with a URL containing the hostname and a hosts-file entry.
Next: browse the SNI-selected site.
Common mistake: sending Host: over HTTPS without SNI and concluding the vhost does not exist. Modern servers frequently split on SNI.
Evidence: the certificate CN/SAN and the page. ## D. Reading the results
Code Meaning Next action
200 exists fetch it, read the app
204 exists, empty body note it; check other methods
301 / 302 redirect follow it; the target directory is the real hit
307 / 308 redirect, method preserved same, but POST bodies survive
401 auth required try default creds, then the credential you hold
403 exists, forbidden bypass attempts below; also try the path with / and with an extension
405 route exists, wrong method re-run with -X POST/-X PUT
429 rate limited slow down (-rate 10, -t 5) — the WAF is watching
500 server error, often exists compare size with baseline; test inputs
503 backend unavailable path may exist; retry later
403 bypass attempts (Documented): ```bash curl -s -H "X-Original-URL: /admin" http:/// curl -s --path-as-is http:///admin/..;/ curl -s http:///admin%2f curl -s http:///ADMIN/ ``` Look for: a 200 where the direct request was 403.
Common mistake: spending 20 minutes on 403 bypasses before checking whether the same content is reachable at another vhost or port. ## E. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | ffuf: all words match | Wildcard / custom 404 | -ac or -fs | | gobuster: the server returns a status code that matches the provided options for non existing urls | Wildcard | --wildcard or switch to ffuf | | feroxbuster: thousands of hits | Wildcard, auto-filter failed | -w smaller list, --filter-size | | Vhost scan finds nothing | Wrong base domain or IP | -u http:// • --append-domain | | DNS scan finds nothing | Wrong resolver | -r | | Tool extremely slow | Through a pivot / many threads | Lower -t, raise --timeout | | 429 everywhere | Rate limit / WAF | -rate 5, randomise -H User-Agent | Pivoting variant. All three tools are TCP-only and work through a proxy, but proxychains serialises connections — reduce concurrency and expect minutes, not seconds: ```bash proxychains4 ffuf -u http:///FUZZ -w -t 5 -timeout 20 -ac proxychains4 gobuster dir -u http:// -w -t 5 proxychains4 feroxbuster -u http:// -w -t 5 ``` Alternatively run the scan from the pivot host (upload the wordlist, use curl loops) and pull the results back. If the target is only reachable through a SOCKS proxy and DNS is internal, add the hostname to /etc/hosts on Kali pointing at the target IP. ## G. Evidence to preserve - The exact command, wordlist path, and filter used. - The baseline 404 status and size. - The hit list, and for each hit the status, size, and a curl -sI of the path. - Vhost results with the default-vhost size they were compared against. - A note of any wildcard found, so the numbers are explainable later. ## H.
