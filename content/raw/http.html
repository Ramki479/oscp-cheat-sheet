Status: Lab Tested = executed against an authorised lab target · Simulated = exercised with simulated output or fixtures · Syntax Checked = flags checked against the installed tool here · Environment Dependent = needs a specific tool, version or host configuration · Documented = standard technique, not run here. ## Prerequisites and execution location - Runs on: Kali Linux. - Needs: curl, whatweb, nikto, openssl, ffuf (installed); sslscan, testssl.sh, hakrawler, katana (optional). - Three tiers, keep them separate: - Passive fingerprinting — headers, titles, certificates. Safe, low noise. - Manual validation — fetch a path, read the response. Still safe. - Intrusive checks — fuzzing, auth attempts, injection probes. Can lock accounts, trigger WAFs or crash the app. Only with authorisation. ## Pivoting variant — internal hosts only proxychains4 curl -i -sS http:/// works for single requests. For anything stateful (sessions, Burp, a browser), forward the port instead: ssh -L 8080::80 @ and browse http://127.0.0.1:8080/ — that keeps cookies, redirects and Burp's proxy chain intact. ## 1. Detect and fingerprint ### Step 01 — Identify the web service Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nmap -sCV -p --script http-title,http-headers,http-methods ``` Look for: server banner, page title, allowed methods (PUT, DELETE are leads), redirects.
Decision: non-standard port or odd banner → Step 02. PUT allowed → note it, do not upload.
Next: Step 02.
Common mistake: scanning only 80/443. Repeat for every HTTP-ish port from the full scan (8080, 8000, 8443, 3000, 5000).
Evidence: the title/server pair for each port — they often differ per vhost. ### Step 02 — Fingerprint the stack Priority: Core · Run on: Kali · Status: Syntax Checked ```bash whatweb -a 1 http:/// whatweb -a 3 http:/// --no-errors ``` Look for: CMS + version, framework, JS libraries, server, cookies set by the app.
Decision: a CMS with a version → search for matching plugins/CVEs. A custom app → go to Step 03 and manual review.
Next: Step 03.
Common mistake: -a 3 is aggressive and detectable; start with -a 1 and only escalate when you need more detail.
Evidence: the plugin/version list. Old page content preserved: the original WhatWeb note also used whatweb --no-errors 192.168.1.0/24 (network sweep) and whatweb -v. Both are valid; the sweep form is only useful on a subnet you own. ## 2. Headers, status codes, redirects, cookies ### Step 03 — Read the response properly Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -i -sS http:/// curl -i -sS -L http:/// -o curl -I -sS https:/// -k ``` Look for: Server:, X-Powered-By:, Set-Cookie:, Location:, security headers that are missing.
Decision: Location: to a hostname → add it to /etc/hosts and re-request. Cookie flags missing (HttpOnly, Secure) → note for later.
Next: Step 04.
Common mistake: -I sends HEAD; some apps behave differently than with GET. Use -i when the body matters.
Evidence: the full header block. Old page content preserved: the original curl note listed curl -v, curl -X POST, and curl -IL. All still valid: -v for the TLS/connection trace, -X POST -d 'a=b' for form posts, -IL for headers after redirects. ### Step 04 — Compare codes and redirects across paths Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash for p in / /admin /login /api /robots.txt; do printf '%-12s ' "$p"; curl -s -o /dev/null -w '%{http_code} %{size_download} %{redirect_url}\n' "http://$p" done ``` Look for: 200 vs 301/302 vs 401/403 vs 404, and different response sizes.
Decision: 401/403 proves the path exists — worth deeper inspection. 302 to /login is normal for a protected app.
Next: Step 05.
Common mistake: treating every 200 as "found" — wildcard/catch-all apps return 200 for everything; compare body sizes.
Evidence: the code/size table. ## 3. robots.txt, sitemap and source ### Step 05 — Read the app's own hints Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -sS http:///robots.txt curl -sS http:///sitemap.xml curl -sS http:/// | grep -Eo '(src|href)="[^"]+"' | sort -u ``` Look for: Disallow: paths, sitemap URLs, script/style references, comments in the HTML.
Decision: any listed path → request it directly. JS files → Step 08.
Next: Step 06.
Common mistake: checking robots only on the main host — each vhost has its own.
Evidence: the disallowed paths and any endpoint-looking URL. ## 4. TLS and certificates ### Step 06 — Inspect the certificate Priority: Core · Run on: Kali · Status: Syntax Checked ```bash openssl s_client -connect :443 -servername /dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName ``` Look for: CN, SANs, validity dates, internal issuer.
Decision: SANs contain hostnames you have not seen → add them to /etc/hosts and probe.
Next: Step 07.
Common mistake: omitting -servername — without SNI you get the default vhost's certificate and miss the rest.
Evidence: the SAN list — often the cheapest source of new hostnames. Old page content preserved: openssl s_client -connect example.com:443 (the original note) is the same command without SNI or the certificate decode pipe. ### Step 07 — Enumerate TLS configuration Priority: Conditional · Run on: Kali · Status: Environment Dependent ```bash sslscan :443 testssl.sh --quiet :443 ``` Prerequisites: sslscan is installed and its flags were checked; testssl.sh is not installed on the build host used for this audit (sudo apt install testssl.sh, or the upstream git checkout on $PATH) — that missing second command is why this step is Environment Dependent. Step 06 (openssl s_client) answers the same certificate questions with no extra tooling. Look for: protocol versions, weak ciphers, expired/self-signed certificates, known TLS CVEs.
Decision: legacy protocols enabled → note it as a hardening finding. It is rarely a direct path to a shell.
Next: Step 09.
Common mistake: reporting a TLS weakness as an exploitation finding — it is a configuration issue unless you can demonstrate impact.
Evidence: the protocol/cipher summary line. ## 5. Virtual-host discovery ### Step 08 — Find hidden vhosts Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ffuf -u http:/// -H "Host: FUZZ." -w -ac -mc all -fc 404 ``` Look for: a different body size or status per Host value.
Decision: a hit → add it to /etc/hosts and run Steps 01-05 against it as a new site.
Next: Step 09.
Common mistake: relying on status codes — many servers return 200 for unknown hosts. Filter by size, or use -ac.
Evidence: the vhost name and its size difference. > Content discovery belongs on one page. Wordlist-driven directory/file brute force (feroxbuster, gobuster, ffuf path mode) is documented in Directory and Virtual Host Enumeration — Complete Command Reference (batch 5). This page covers the manual and fingerprinting side only, so the two never drift apart. ## 6. Authentication mechanisms ### Step 09 — Identify the auth type Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -i -sS http:///admin curl -i -sS -u : http:///admin ``` Look for: WWW-Authenticate: Basic realm=... (HTTP Basic), a login form in the HTML (form/session), Set-Cookie after login.
Decision: Basic auth → credentials are sent in every request; try found credentials. Form login → capture the request in Burp and replay it.
Next: Step 10.
Common mistake: assuming a 401 means "no access" — it often confirms the path exists and tells you the realm name.
Evidence: the WWW-Authenticate header or the form's action/method. ### Step 10 — Session handling Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash curl -i -sS -c cookies.txt -d 'username=&password=' http:///login curl -sS -b cookies.txt http:///dashboard ``` Look for: a session cookie, then a successful authenticated page.
Decision: session works → browse the authenticated surface; it is usually where the vulnerability lives.
Next: Step 11.
Common mistake: guessing the form field names — copy them from the actual HTML or Burp.
Evidence: the request that authenticated and the response that proved it. ## 7. JavaScript and endpoint discovery ### Step 11 — Mine the JavaScript Priority: Core · Run on: Kali · Status: Syntax Checked ```bash curl -sS http:/// | grep -Eo 'src="[^"]+\.js[^"]*"' | sort -u curl -sS http:///js/app.js | grep -Eo '"/[a-zA-Z0-9_/.-]+"' | sort -u ``` Look for: API paths, hidden admin routes, API keys, feature flags.
Decision: endpoints found → request them (Step 04) and check for missing auth.
Next: Step 12.
Common mistake: only reading the visible page — SPAs put everything in the bundle.
Evidence: the endpoint list with the file it came from. ### Step 12 — Crawl with a tool Priority: Conditional · Run on: Kali · Status: Environment Dependent ```bash hakrawler -url http:// -depth 3 -plain katana -u http:// -d 3 -silent ``` Prerequisites: hakrawler (go install github.com/hakluke/hakrawler@latest) and katana (go install github.com/projectdiscovery/katana/cmd/katana@latest) — neither is installed on the build host used for this audit, hence Environment Dependent. The curl + grep crawl at Step 11 and feroxbuster at Step 14 need no extra tooling. Look for: URLs, parameters, forms, JS files.
Decision: new endpoints → Step 04. Nothing new → the app is small; go manual.
Next: Step 04 (new endpoints) or Step 14 (manual validation).
Common mistake: crawlers miss authenticated areas — replay with a session cookie.
Evidence: the URL list. Old page content preserved: the original notes had hakrawler -url http://TARGET and katana -u http://TARGET -d 3; the forms above add -plain/-silent for pipe-friendly output. ## 8. Application-level manual testing ### Step 13 — Broad scanner pass Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash nikto -h http:// nikto -h https:// -ssl ``` Look for: dangerous files, outdated components, missing headers, exposed directories.
Decision: every hit must be manually reproduced before it goes in the report.
Next: Step 14.
Common mistake: reporting Nikto output verbatim — it is noisy and produces false positives.
Evidence: only the confirmed findings. Old page content preserved: the original Nikto note also used nikto -h TARGET -p 8080 for a non-standard port; that form is still correct. ### Step 14 — Manual validation checklist Priority: Core · Run on: Kali · Status: Documented - Parameters — try a quote (') and watch for SQL errors; try ../../ for traversal. - File upload — extension filtering, content-type checks, upload directory reachable over HTTP. - Auth logic — forced browsing, IDOR (change an object id), default credentials. - Verbose errors — stack traces reveal paths, frameworks and sometimes credentials. - Known CMS plugins — enumerate versions, match against public advisories. > Only run the intrusive items above where the engagement allows it. On the exam, an unrequested destructive test can invalidate a machine. ### Step 15 — Consider automated scanners carefully Priority: Advanced · Run on: Kali · Status: Documented
Automated web scanners (sqlmap with aggressive options, nuclei, wapiti) may be restricted by the current exam rules. Confirm with the current official OffSec exam guide before relying on one. Manual validation is always permitted and usually faster on a small app. ## 9. Burp Suite handoff ### Step 16 — Get traffic into Burp Priority: Core · Run on: Kali + browser · Status: Documented 1. Browser proxy → 127.0.0.1:8080 (or use FoxyProxy with a profile). 2. Install Burp's CA: browse to http://burp/cert, import into the browser trust store. 3. Set Target → Scope to the lab host so history stays readable. 4. curl requests can be replayed: copy as curl from Burp, or send a request to Repeater and edit it. Look for: requests that differ from the browser's (hidden parameters, JSON bodies, custom headers).
Decision: an endpoint worth manipulating → Repeater. A parameter worth enumerating → Intruder (mind the rate).
Next: return to Step 14 with real requests.
Common mistake: testing without Burp's proxy in scope, then losing the request that worked.
Evidence: export the request/response pair for the report. ## 10. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | curl: (60) SSL certificate problem | Self-signed cert | -k | | curl: (7) Failed to connect | Wrong port, or service bound to [localhost](http://localhost) | Re-check the port scan; pivot through the host | | Redirect loop | Cookie or host mismatch | Use the hostname from Location, not the IP | | 403 on every path | WAF or IP allow-list | Slow down, change User-Agent, check for vhosts | | 200 on everything | Catch-all/wildcard | Filter by size (-fs), not status | | Empty body but 200 | JS-rendered SPA | Read the bundle (Step 11) | | Site works with IP, breaks with hostname | Missing /etc/hosts entry | Add it | | nikto finds nothing | Wrong scheme/port | Try -ssl, and the exact port | Stop condition: when headers, source, robots and one manual pass produce no lead, move to another service. Re-fuzzing the same wordlist is not new information. ## 11. Quick workflow 1. nmap -sCV -p --script http-title,http-headers. 2. whatweb -a 1 → -a 3 if needed. 3. curl -i -sS -L — headers, redirects, cookies. 4. robots.txt, sitemap.xml, page source. 5. openssl s_client ... subjectAltName — new hostnames. 6. ffuf vhost discovery → add names to /etc/hosts. 7. Auth: identify mechanism, capture a session. 8. JS: endpoints and hidden routes. 9. nikto for breadth, then manual validation. 10. Burp for anything stateful. 11. Directory brute force → the Directory & VHost page. ## 12. Evidence to preserve - The header block per port (server, framework, cookies). - Certificate SAN list. - Every vhost/hostname you added to /etc/hosts. - The authenticated request/response pair. - Confirmed Nikto findings only, each with a manual reproduction. ## 13.
