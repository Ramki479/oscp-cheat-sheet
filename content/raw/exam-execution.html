> Purpose: the exam is scored on flags plus evidence, not on shells. Build the workspace, capture proof in a form a grader accepts, and keep a timeline — before exam day, so it is habit rather than panic. ## Scoring context - Three standalone machines (60 points) plus one Active Directory set of three machines (40 points), 23 hours 45 minutes, then 24 hours to upload the report. - AI chatbots and similar assistants are prohibited during the exam. - Scoring is scaled from 1 December 2026; the current guide no longer restates a raw pass mark — confirm with the current official guide. - Full rules: OSCP Exam Rules & Tool Restrictions. No page here overrides the official guide. ## A. Workspace ### Step 01 — Create the workspace Priority: Core · Run on: Kali · Status: Syntax Checked ```bash mkdir -p ~/exam/{scans,loot,screens,notes} ls -la ~/exam ``` Look for: four directories, created once, at the start.
Decision: every artefact goes into one of them — scans by host, loot by host, screenshots by sequence, notes by host.
Next: Step 02.
Common mistake: saving evidence to ~/Downloads or /tmp. Files there get lost on reboot or collided between hosts.
Evidence: the directory listing. ### Step 02 — Naming discipline Priority: Core · Run on: Kali · Status: Syntax Checked ```bash mkdir -p ~/exam/scans/ ~/exam/loot/ # scans: ~/exam/scans//nmap_full.txt # loot: ~/exam/loot//_.txt # shots: ~/exam/screens/__.png ``` Look for: a path you can reconstruct a week later.
Decision: host-first naming (__) sorts correctly and survives copy/paste into the report.
Next: Step 03.
Common mistake: screenshot1.png. Twenty of those and you cannot tell which host or which privilege level it proves.
Evidence: the naming scheme in use. ## B. Capture proof ### Step 03 — Linux host proof Priority: Core · Run on: Linux target · Status: Syntax Checked ```bash whoami; hostname; ip a; cat /etc/hostname cat /root/local.txt cat /root/proof.txt ``` Look for: the flag contents, plus hostname/IP visible in the same terminal.
Decision: local.txt proves user, proof.txt proves root — capture both at the moment you obtain them.
Next: screenshot immediately (Step 06).
Common mistake: capturing the flag, then closing the shell, then having no proof of which host it came from.
Evidence: one screen showing the command, the flag, and ip a/hostname. ### Step 04 — Windows host proof Priority: Core · Run on: Windows target · Status: Syntax Checked ```shen whoami; hostname; ipconfig type C:\Users\\Desktop\local.txt type C:\Users\Administrator\Desktop\proof.txt ``` Look for: nt authority\system or the Administrator context, the hostname, the IPv4 address, and the flag.
Decision: Administrator vs SYSTEM matters for the write-up — state which account you used.
Next: screenshot (Step 06).
Common mistake: running type in a different session from whoami. The grader must see them together.
Evidence: the combined output in one screenshot. ### Step 05 — Read local and proof files Priority: Core · Run on: either · Status: Syntax Checked ```bash cat /root/proof.txt 2>/dev/null ``` ```cmd type C:\Users\Administrator\Desktop\proof.txt 2>nul ``` Look for: the correct file for the privilege level you reached.
Decision: local.txt without proof.txt means the box is half-done — do not move on and forget it.
Next: continue escalation, then recapture.
Common mistake: copying the flag into notes without a screenshot. Notes are supporting evidence; the screenshot is the proof.
Evidence: the file path and the flag value. ### Step 06 — Screenshot with a naming scheme Priority: Core · Run on: Kali or VM host · Status: Documented ```bash scrot -s ~/exam/screens/$(date +%H%M%S)_proof.png # alternative, if scrot is unavailable: use the hypervisor/VM screenshot tool ``` Look for: a PNG that includes the flag and the host identity.
Decision: scrot is not installed on this host — install it on your own exam VM, or use the VM console's screenshot function. Test the chosen method before exam day.
Next: Step 11 (hash it).
Common mistake: cropping the screenshot so the hostname/IP disappears. Never crop the terminal header.
Evidence: the PNG file itself, named with host and purpose. ### Step 07 — The one-image rule Priority: Core · Run on: either · Status: Documented A grader should be able to look at one image and see: the flag, the account, and the host. If a single terminal cannot show all three (e.g. a GUI-only path), take two consecutive screenshots and label them _proof_a and _proof_b. Look for: no ambiguity about which machine the flag belongs to.
Decision: you cannot prove host identity → the flag is worth nothing in a dispute. Recapture.
Next: hash and file it.
Common mistake: proving root access with a screenshot of id only. That shows a privilege level, not a completed box.
Evidence: the paired images, sequentially numbered. ## C. Timeline and notes ### Step 08 — Timestamp your activity Priority: Core · Run on: Kali · Status: Syntax Checked ```bash date -u; date +%H:%M:%S >> ~/exam/notes/timeline.txt ``` Look for: a monotonic log of what you did and when.
Decision: useful when the report needs "initial access at …", and when you must explain a gap.
Next: append a one-line entry at each major milestone.
Common mistake: writing the timeline at the end from memory. It will be wrong, and it reads like it.
Evidence: ~/exam/notes/timeline.txt. ### Step 09 — Per-machine notes Priority: Core · Run on: Kali · Status: Syntax Checked Use the OSCP Machine Notes — Template page for every host: IP, hostname, open ports, credentials found, exploitation path, privilege escalation, flags, and screenshot filenames. Look for: enough detail that you could redo the box from the notes alone.
Decision: if a step produced a credential or a shell, it belongs in the notes and in the final report.
Next: Step 10.
Common mistake: notes that record only the final command. The report needs the path, including failed branches that explain your choices.
Evidence: one note file per host. ### Step 10 — Time budget Priority: Core · Run on: — · Status: Documented A workable split for 23h45m: roughly 12 hours for the three standalone machines, 6-7 hours for the AD set, and the remaining time for reporting and re-checks. Treat these as targets, not rules — the official guide is authoritative on timing. Look for: a box that has consumed its budget without a foothold.
Decision: park it, take the easy points elsewhere, come back with fresh eyes.
Next: move to the next target and log the switch in the timeline.
Common mistake: sinking 8 hours into one machine while three others remain untouched.
Evidence: the budget vs actual, in the timeline. ## D. Integrity and recovery ### Step 11 — Hash the evidence Priority: Core · Run on: Kali · Status: Syntax Checked ```bash md5sum ~/exam/screens/*.png ~/exam/loot/* 2>/dev/null sha256sum ~/exam/screens/*.png ``` Look for: a hash list you can re-verify before upload.
Decision: hashes differ after copying → the copy corrupted (rare); re-copy before submitting.
Next: keep the hash file with the report.
Common mistake: hashing an empty glob (no files matched) and calling it verified. Check the file count first.
Evidence: the hash list and the matching files. ### Step 12 — Revert a broken target Priority: Conditional · Run on: exam console · Status: Documented If an exploit crashes a service or you lock yourself out, revert the machine to the exam-provided snapshot before re-attacking. Re-read the exam guide for the exact revert procedure and any scoring implications. Look for: the documented revert control in the exam environment — not a guess at vmrun or a hypervisor CLI.
Decision: the box is unstable or credentials are bricked → revert, then redo only the steps needed to regain your position.
Next: re-capture proof if the revert lost it.
Common mistake: reverting after you already captured the flag and losing the shell state — capture and hash proof before any revert.
Evidence: the timeline entry for the revert and the reason. ## E. Report skeleton | Section | Contents | | --- | --- | | Summary | Machines compromised, flags, and the AD set status | | Per host | IP, hostname, ports, initial access, privesc, flags, screenshots | | AD set | Each host plus the domain controller; the path taken | | Evidence index | Screenshot filenames and hashes | | Appendix | Tool output that supports a claim (nmap, secretsdump redacted) | Rule: every claim in the report points to a screenshot or a command output. If it is not evidenced, do not claim it. ## F. Decision tree | Situation | Do this | Do not | | --- | --- | --- | | Starting the exam | Workspace + naming (Steps 01-02) | Start scanning with no structure | | Got user | Capture local.txt • host identity | Wait until root | | Got root/SYSTEM | Capture proof.txt in the same shell | Close the shell first | | Screenshot has no host identity | Recapture (Step 07) | Crop it later | | Box crashes | Revert snapshot (Step 12) | Improvise a repair | | Behind schedule | Park the box, log it (Step 10) | Sink the remaining time | | Writing the report | Follow the skeleton (Section E) | Paste raw terminal output | ## G. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | Screenshot tool missing | Not installed on Kali | Install before exam day, or use the VM console | | Flag screenshot rejected in review | No host identity | Recapture with ip a/ipconfig visible | | md5sum: no such file | Glob matched nothing | Check the directory, then re-hash | | Notes unusable | Written after the fact | Use the per-machine template live | | Report missing a step | Relied on memory | Timeline + notes (Steps 08-09) | | Revert lost the shell | Reverted after capture | Capture and hash first | ## H. Pre-submission checklist - Every flag has a screenshot showing the flag, account, and host. - Every machine has a note file and a report section. - Screenshots are named by host and purpose, and hashed. - The AD set documents all three hosts and the domain controller. - No claim lacks a command output. - Report uploaded within the 24-hour window. ## I.
