Verification note Priority: Core = run it almost always · Conditional = when a finding justifies it · Advanced = specialised, do not let it displace core enumeration.
Status: Lab Tested = executed against an authorised lab target · Simulated = exercised with simulated output or fixtures · Syntax Checked = flags checked against the installed tool here · Environment Dependent = needs a specific tool, version or host configuration · Documented = standard technique, not run here. ## Prerequisites and execution location - Runs on: Kali Linux. - Needs: sudo for SYN, UDP and OS scans; a route to ; confirmed scope. - Output convention: write every scan into (./recon//). ## 1. Scope and target ### Step 01 — Confirm connectivity before blaming the target Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: separate "target is down" from "my tunnel is broken". ```bash ip a; ip route get ; ping -c 3 ``` Look for: tun0 with an IP, a route whose dev is that interface, ICMP replies.
Decision: no route → reconnect the VPN. Route present but no reply → continue; most exam targets drop ICMP.
Next: Step 02.
Common mistake: scanning your own VPN subnet, or an IP left over from the previous box.
Evidence: note the confirmed IP in the machine notes. ### Step 02 — Create the output directory Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: every scan lands somewhere predictable and survives the box. ```bash mkdir -p && cd ``` Look for: no output = success.
Decision: if the directory exists, reuse it — never delete earlier scans.
Next: Step 03.
Common mistake: scanning from ~ and losing the files among other boxes' output.
Evidence: the directory becomes part of the report trail. ## 2. Host discovery ### Step 03 — Ping sweep Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: find live hosts in a range without probing ports. ```bash nmap -sn /24 -oN ``` Look for: Nmap scan report for per live host.
Decision: a host missing here may still be up (ICMP filtered). For a single known target, skip straight to Step 04 with -Pn.
Next: Step 04 on each live host.
Common mistake: treating -sn as a port scan — it sends no TCP or UDP port probes, so it cannot find services.
Evidence: the host list, if you are enumerating a subnet. ## 3. Port discovery > Why two scans? The default scan covers the 1,000 most common ports and finishes in seconds-to-minutes — it is the fast first look. A 65,535-port scan finds services on high ports (8080, 8443, 5985, 49152+) that the default list never touches. Run the fast scan first so you have something to work with, then the full scan to close the gap. ### Step 04 — Initial TCP scan (top 1,000) Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: quick baseline of the ports most likely to matter. ```bash sudo nmap -sS -T4 -oN ``` Look for: open lines, and any filtered ports with a reason.
Decision: open ports → Step 06. All 1,000 filtered → Step 05 with -Pn, then review filtering.
Next: Step 05 (full range) — do not stop at the top 1,000.
Common mistake: presenting the top-1,000 result as "all ports" and missing the second web app on 8081.
Evidence: the normal-format file. ### Step 05 — Full TCP port discovery Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: find every listening TCP service. ```bash sudo nmap -p- --min-rate 5000 -T4 -oA ``` Look for: any open port not present in Step 04 — these are usually the interesting ones.
Decision: if the scan finishes suspiciously fast or reports host seems down, drop --min-rate and retry with -T3. False negatives are worse than a slow scan.
Next: Step 06 on the complete open-port list.
Common mistake: --min-rate 5000 on a lossy link drops packets → missed ports. Lower the rate before trusting an empty result.
Evidence: keep the .nmap, .gnmap and .xml from -oA. ### Step 06 — Targeted version and script scan Priority: Core · Run on: Kali · Status: Syntax Checked
Purpose: identify the exact product/version on the ports you actually found. ```bash sudo nmap -sCV -p -oA ``` Look for: VERSION column (product, version, extra info, OS hints) plus default-script output: titles, hostnames, certificates, share names.
Decision: version known → search for matching CVEs and move to Step 13-18 for the service's NSE scripts. Version hidden (tcpwrapped) → try --version-all (Step 08).
Next: Step 07 if a port looks filtered; otherwise Step 08.
Common mistake: running -sC -p- in one pass — it is extremely slow. Restrict scripts to discovered ports.
Evidence: the scan plus the port/service table you will paste into the report. ### Step 07 — Investigate a filtered or ambiguous port Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: distinguish filtered, closed and open-but-silent. ```bash sudo nmap -sS -p --reason --max-retries 3 ``` Look for: the REASON column (syn-ack, reset, no-response).
Decision: reset = closed · no-response = filtered or heavily rate-limited · syn-ack = open.
Next: if filtered, test the same service on an alternate port or move on; do not loop.
Common mistake: assuming "filtered" means "nothing is there" — a firewall may simply be dropping your probe.
Evidence: the reason table, if you later report a filtered service. ## 4. Service and version detection ### Step 08 — Heavier version detection Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: squeeze a version out of a service that returned little. ```bash sudo nmap -sV --version-all -p ``` Look for: a fuller VERSION string, sometimes with build numbers.
Decision: still nothing → banner-grab manually (nc) or use the service's own client.
Next: Step 13 for the relevant service family.
Common mistake: expecting -sV to identify vulnerabilities. It reports a version banner; it does not prove a service is vulnerable.
Evidence: the version string you will match against exploit databases. ### Step 09 — Default scripts without version detection Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: get script output quickly when you already know the version. ```bash sudo nmap -sC -p ``` Look for: titles, headers, certificate subjects, share and user listings.
Decision: a script error usually means the service is not what the port suggested — confirm with Step 06.
Next: the service-specific section below.
Common mistake: -sC includes http-title etc. but is not a vulnerability scan.
Evidence: any hostname or username revealed here — it feeds DNS and vhost work. ## 5. UDP scanning ### Step 10 — Top UDP ports Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: catch services that only speak UDP (DNS 53, SNMP 161, NTP 123, IPMI 623, TFTP 69). ```bash sudo nmap -sU --top-ports 50 --open -T4 -oN ``` Look for: open or open|filtered.
Decision: open|filtered is normal and ambiguous — confirm with the service's own client (dig, snmpwalk) rather than rescanning.
Next: Step 11 for a suspected service, then its tool page.
Common mistake: scanning all 65,535 UDP ports on the exam clock. It takes hours.
Evidence: the UDP table; note which ports were confirmed by a real client. ### Step 11 — Targeted UDP with a script Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: confirm and fingerprint one UDP service. ```bash sudo nmap -sU -p --script snmp-info,ipmi-version ``` Look for: a script response — that alone proves the port is open.
Decision: no response → treat as filtered and move on.
Next: SNMP → SNMP page · IPMI → note the firmware version.
Common mistake: mixing UDP and TCP ports in one -p list without -sU; nmap scans them as TCP.
Evidence: the script output block. ## 6. OS detection ### Step 12 — OS fingerprint Priority: Conditional · Run on: Kali · Status: Syntax Checked
Purpose: decide between Linux and Windows tooling early. ```bash sudo nmap -O --osscan-guess -p ``` Look for: OS details: or Aggressive OS guesses:.
Decision: one clean match → trust it enough to pick tools. No match → use service banners and TTL instead.
Next: choose the matching privilege-escalation page later.
Common mistake: reading a single "Linux 4.x" guess as fact — VMs and firewalls routinely mislead it.
Evidence: the OS guess plus the evidence you actually relied on (banner, TTL). ## 7. Service-specific NSE ### Step 13 — HTTP / HTTPS family Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nmap -p --script http-title,http-headers,http-methods,http-enum,http-robots.txt ``` Look for: page title, Server: header, allowed methods (PUT is interesting), enumerated paths, robots entries.
Decision: paths found → fetch them manually. PUT allowed → note it as a lead, do not upload yet.
Next: [HTTP & HTTPS — Complete Command Reference](https://app.notion.com/p/4011e51238b581649211c0c5db9c94f8) for the full web workflow.
Common mistake: http-enum is noisy and slow against large apps; it is a lead generator, not a directory brute-forcer.
Evidence: titles and paths; they are often the fastest route into the app. ### Step 14 — SMB family Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nmap -p139,445 --script smb-os-discovery,smb2-security-mode,smb-enum-shares,smb-enum-users ``` Look for: hostname/domain/OS, signing: enabled|disabled, share names, account names.
Decision: shares listed → go to [SMB — Complete Command Reference](https://app.notion.com/p/4011e51238b581bbadcbe10d66d5ce31). Signing disabled → relay becomes worth investigating (prerequisites still apply).
Next: [SMB — Complete Command Reference](https://app.notion.com/p/4011e51238b581bbadcbe10d66d5ce31) Step 05.
Common mistake: reading "signing disabled" as "relay will work". You still need a coercible authentication and a target that accepts the relayed identity.
Evidence: the OS/domain block — it is often the first proof you are facing a domain-joined host. ### Step 15 — FTP family Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nmap -p21 --script ftp-anon,ftp-syst,ftp-vsftpd-backdoor ``` Look for: Anonymous FTP login allowed, server type/features, backdoor response.
Decision: anonymous allowed → [FTP — Complete Command Reference](https://app.notion.com/p/4011e51238b581df8e65eb2517720af2) Step 04. Backdoor script positive → validate manually before any exploit.
Next: [FTP — Complete Command Reference](https://app.notion.com/p/4011e51238b581df8e65eb2517720af2).
Common mistake: firing a vsftpd exploit because the version is 2.3.4 — most 2.3.4 builds are not the backdoored one.
Evidence: the version banner and the anonymous result. ### Step 16 — DNS Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash nmap -p53 --script dns-nsid,dns-zone-transfer --script-args dns-zone-transfer.domain= ``` Look for: zone-transfer: records, or a transfer refusal.
Decision: transfer succeeds → every hostname goes into /etc/hosts and gets probed. Refused → normal; brute-force instead.
Next: [DNS — Complete Command Reference](https://app.notion.com/p/4011e51238b581b49f33e6d71a304549).
Common mistake: running dns-zone-transfer without --script-args — the script has no domain to ask for.
Evidence: the full zone dump, if you get one. ### Step 17 — SSH Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash nmap -p22 --script ssh-auth-methods,ssh2-enum-algos ``` Look for: accepted auth methods; weak KEX/ciphers/host-key algorithms.
Decision: publickey only + a key found on disk = worth trying. Password allowed → one careful attempt, not a brute force.
Next: [SSH — Complete Command Reference](https://app.notion.com/p/4011e51238b58123b446cc627bc02913).
Common mistake: treating weak algorithms as an authentication bypass. They are not.
Evidence: the auth-method line, before you attempt a login. ### Step 18 — Database services Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash nmap -p3306 --script mysql-info nmap -p1433 --script ms-sql-info,ms-sql-ntlm-info ``` Look for: protocol version, auth salt, instance name, NTLM domain/host info.
Decision: MSSQL info leaks a domain name → useful for AD enumeration even before credentials.
Next: Other Services — Complete Command Reference (MySQL and MSSQL).
Common mistake: ms-sql-ntlm-info needs the instance to answer pre-auth; silence is not a closed port.
Evidence: instance and domain strings. ### Step 19 — Broad vulnerability category Priority: Advanced · Run on: Kali · Status: Syntax Checked ```bash sudo nmap --script vuln -p ``` Look for: VULNERABLE blocks with CVE references.
Decision: every hit is a lead, not a finding — reproduce manually before reporting or exploiting.
Next: validate, then exploit research.
Common mistake: running this against fragile services on the exam; some scripts can crash a daemon and cost you the box.
Evidence: the CVE IDs, with the manual reproduction that confirmed them. ### Step 20 — Find the right script Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ls /usr/share/nmap/scripts | grep -i grep -l "categories" /usr/share/nmap/scripts/*.nse | head ``` Look for: a script name matching the service in front of you.
Decision: no script → read the service's own documentation; NSE coverage is not exhaustive.
Next: run the script with --script-help first.
Common mistake: guessing a script name. --script-help and the directory listing are authoritative.
Evidence: the exact script name you used, so the scan is reproducible. ## 8. Output and evidence ### Step 21 — Save every format Priority: Core · Run on: Kali · Status: Syntax Checked ```bash sudo nmap -sCV -p -oA ``` Look for: three files appear: .nmap (readable), .gnmap (grep-able), .xml (machine-readable).
Decision: use .gnmap for quick greps (grep open *.gnmap), .xml for reporting tools.
Next: Step 22 if you want an HTML appendix.
Common mistake: using -oN everywhere and later having to re-scan for structured data.
Evidence: all three files belong in . ### Step 22 — Turn XML into an HTML appendix Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash xsltproc -o .html /usr/share/nmap/nmap.xsl .xml ``` Look for: a readable HTML file with the port table.
Decision: useful for the report appendix; not required for scoring.
Next: attach or reference it in the report notes.
Common mistake: passing the .nmap file instead of the .xml.
Evidence: the HTML file plus the original XML. ## 9. Performance and timing ### Step 23 — Tune a slow or lossy scan Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash sudo nmap -p- -T3 --max-retries 2 --host-timeout 30m -oN ``` Look for: fewer no-response ports and a stable completion.
Decision: still missing ports → scan in ranges (-p 1-10000, -p 10001-20000) so a failure is contained.
Next: Step 06 on the confirmed list.
Common mistake: raising -T to compensate for packet loss. It makes loss worse.
Evidence: the timing options used — they explain why two scans differ. ### Step 24 — Why aggressive timing lies Priority: Core (read) · Run on: Kali · Status: Documented
Purpose: decide when speed is safe. - -T4 is a reasonable default on a lab VPN. - -T5 and very high --min-rate values cause dropped probes and false negatives. - --max-retries 0 turns every lost packet into a missing port. - Fragmentation (-f), decoys (-D) and spoofed source ports are conditional — they exist to test filtering, not to be defaults, and -D produces false positives in host lists. ## 10. Through a pivot ### Step 25 — Scan an internal host through SOCKS Priority: Conditional · Run on: Kali, with a SOCKS proxy already running · Status: Syntax Checked ```bash proxychains4 nmap -sT -Pn -n -p ``` Look for: a result at all — proxied scans are slow and lossy.
Decision: timeout → raise the proxy timeout and scan a single port; a whole-range scan through SOCKS is rarely worth it.
Next: once the port list is known, use the service's own client through the proxy.
Common mistake: -sS through proxychains — SYN scans cannot traverse a SOCKS proxy; you must use -sT.
Evidence: note that the result came via proxy; the report should say so. > Pivoting variant (all pages): if you are targeting an internal host, prepend proxychains4 and add -Pn to skip host discovery, which usually fails through a proxy. ## 11. Reading the results | State | Meaning | What to do | | --- | --- | --- | | open | A service accepted the connection | Enumerate it | | closed | Host replied with RST; nothing listening | No further action | | filtered | No reply — firewall dropped it | Try --reason, alternate ports, or move on | | open\|filtered | Cannot tell (UDP, or a firewall that eats RSTs) | Confirm with the service's own client | - Version strings are banners, not vulnerability proof. Apache httpd 2.4.49 tells you which CVEs to research; it does not tell you the path is exploitable. - TTL near 64 suggests Linux/Unix, near 128 suggests Windows — a hint for tool selection, never a finding. - A single open port on a host with everything else filtered is a strong signal: it is probably the intended path. ## 12. Troubleshooting | Symptom | Likely cause | Fix | | --- | --- | --- | | Host seems down | ICMP blocked | Add -Pn | | All ports filtered | Host firewall, or wrong IP | Verify with ip route get; try a known-open port | | Scan hangs on one port | Service accepts but never replies | --host-timeout, or scan that port with nc -w 3 | | Missing ports found by another tool | Rate too high / packet loss | Drop --min-rate, use -T3, retry the port | | Failed to resolve | Hostname not in DNS or /etc/hosts | Use the IP, or add the entry | | QUITTING! early | Interface changed mid-scan | Confirm VPN stability, rerun | Stop condition: if two different scan strategies agree on the port list, stop scanning and start enumerating. Re-scanning the same host with the same options does not produce new information. ## 13. Quick workflow 1. ip a; ip route get — prove connectivity. 2. mkdir -p — set the evidence path. 3. nmap -sn — only when sweeping a subnet. 4. sudo nmap -sS -T4 -oN ... — fast baseline. 5. sudo nmap -p- --min-rate 5000 -T4 -oA ... — complete port list. 6. sudo nmap -sCV -p -oA ... — identify what is open. 7. UDP top-50 — if the host looks sparse or a UDP service is suspected. 8. Service NSE — Steps 13-18 for every service you found. 9. Save .nmap/.gnmap/.xml, then open the matching tool page. ## 14. Evidence to preserve - The three output files from -oA (do not overwrite them on a retry — use a new name). - The command line itself, including timing options. - Any hostname, domain, share or username revealed by NSE — these are credentials-adjacent. - A screenshot of the port table if the report requires visual proof. ## 15.
