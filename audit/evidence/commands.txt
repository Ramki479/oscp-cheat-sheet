
===== PAGE nmap | Nmap — Complete Command Reference =====

[nmap-01] 01. Confirm connectivity before blaming the target | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
ip a; ip route get <TARGET_IP>; ping -c 3 <TARGET_IP>
LOOKFOR: `tun0` with an IP, a route whose `dev` is that interface, ICMP replies.
DECISION: no route → reconnect the VPN. Route present but no reply → continue; most exam targets drop ICMP.
NEXT: Step 02.
MISTAKE: scanning your own VPN subnet, or an IP left over from the previous box.
EVIDENCE: note the confirmed IP in the machine notes.

[nmap-02] 02. Create the output directory | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
mkdir -p <OUTPUT_DIR> && cd <OUTPUT_DIR>
LOOKFOR: no output = success.
DECISION: if the directory exists, reuse it — never delete earlier scans.
NEXT: Step 03.
MISTAKE: scanning from `~` and losing the files among other boxes' output.
EVIDENCE: the directory becomes part of the report trail.

[nmap-03] 03. Ping sweep | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -sn <TARGET_IP>/24 -oN <OUTPUT_FILE>
LOOKFOR: `Nmap scan report for ` per live host.
DECISION: a host missing here may still be up (ICMP filtered). For a single known target, skip straight to Step 04 with `-Pn`.
NEXT: Step 04 on each live host.
MISTAKE: treating `-sn` as a port scan — it sends no TCP or UDP port probes, so it cannot find services.
EVIDENCE: the host list, if you are enumerating a subnet.

[nmap-04] 04. Initial TCP scan (top 1,000) | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sS -T4 -oN <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: `open` lines, and any filtered ports with a reason.
DECISION: open ports → Step 06. All 1,000 filtered → Step 05 with `-Pn`, then review filtering.
NEXT: Step 05 (full range) — do not stop at the top 1,000.
MISTAKE: presenting the top-1,000 result as "all ports" and missing the second web app on 8081.
EVIDENCE: the normal-format file.

[nmap-05] 05. Full TCP port discovery | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -p- --min-rate 5000 -T4 -oA <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: any `open` port not present in Step 04 — these are usually the interesting ones.
DECISION: if the scan finishes suspiciously fast or reports `host seems down`, drop `--min-rate` and retry with `-T3`. False negatives are worse than a slow scan.
NEXT: Step 06 on the complete open-port list.
MISTAKE: `--min-rate 5000` on a lossy link drops packets → missed ports. Lower the rate before trusting an empty result.
EVIDENCE: keep the `.nmap`, `.gnmap` and `.xml` from `-oA`.

[nmap-06] 06. Targeted version and script scan | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sCV -p <TARGET_PORT> -oA <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: `VERSION` column (product, version, extra info, OS hints) plus default-script output: titles, hostnames, certificates, share names.
DECISION: version known → search for matching CVEs and move to Step 13-18 for the service's NSE scripts. Version hidden (`tcpwrapped`) → try `--version-all` (Step 08).
NEXT: Step 07 if a port looks filtered; otherwise Step 08.
MISTAKE: running `-sC -p-` in one pass — it is extremely slow. Restrict scripts to discovered ports.
EVIDENCE: the scan plus the port/service table you will paste into the report.

[nmap-07] 07. Investigate a filtered or ambiguous port | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sS -p <TARGET_PORT> --reason --max-retries 3 <TARGET_IP>
LOOKFOR: the `REASON` column (`syn-ack`, `reset`, `no-response`).
DECISION: `reset` = closed · `no-response` = filtered or heavily rate-limited · `syn-ack` = open.
NEXT: if filtered, test the same service on an alternate port or move on; do not loop.
MISTAKE: assuming "filtered" means "nothing is there" — a firewall may simply be dropping your probe.
EVIDENCE: the reason table, if you later report a filtered service.

[nmap-08] 08. Heavier version detection | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sV --version-all -p <TARGET_PORT> <TARGET_IP>
LOOKFOR: a fuller `VERSION` string, sometimes with build numbers.
DECISION: still nothing → banner-grab manually (`nc`) or use the service's own client.
NEXT: Step 13 for the relevant service family.
MISTAKE: expecting `-sV` to identify vulnerabilities. It reports a version banner; it does **not** prove a service is vulnerable.
EVIDENCE: the version string you will match against exploit databases.

[nmap-09] 09. Default scripts without version detection | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sC -p <TARGET_PORT> <TARGET_IP>
LOOKFOR: titles, headers, certificate subjects, share and user listings.
DECISION: a script error usually means the service is not what the port suggested — confirm with Step 06.
NEXT: the service-specific section below.
MISTAKE: `-sC` includes `http-title` etc. but is not a vulnerability scan.
EVIDENCE: any hostname or username revealed here — it feeds DNS and vhost work.

[nmap-10] 10. Top UDP ports | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sU --top-ports 50 --open -T4 -oN <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: `open` or `open|filtered`.
DECISION: `open|filtered` is normal and ambiguous — confirm with the service's own client (`dig`, `snmpwalk`) rather than rescanning.
NEXT: Step 11 for a suspected service, then its tool page.
MISTAKE: scanning all 65,535 UDP ports on the exam clock. It takes hours.
EVIDENCE: the UDP table; note which ports were confirmed by a real client.

[nmap-11] 11. Targeted UDP with a script | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sU -p <TARGET_PORT> --script snmp-info,ipmi-version <TARGET_IP>
LOOKFOR: a script response — that alone proves the port is open.
DECISION: no response → treat as filtered and move on.
NEXT: SNMP → SNMP page · IPMI → note the firmware version.
MISTAKE: mixing UDP and TCP ports in one `-p` list without `-sU`; nmap scans them as TCP.
EVIDENCE: the script output block.

[nmap-12] 12. OS fingerprint | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -O --osscan-guess -p <TARGET_PORT> <TARGET_IP>
LOOKFOR: `OS details:` or `Aggressive OS guesses:`.
DECISION: one clean match → trust it enough to pick tools. No match → use service banners and TTL instead.
NEXT: choose the matching privilege-escalation page later.
MISTAKE: reading a single "Linux 4.x" guess as fact — VMs and firewalls routinely mislead it.
EVIDENCE: the OS guess plus the evidence you actually relied on (banner, TTL).

[nmap-13] 13. HTTP / HTTPS family | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p <TARGET_PORT> --script http-title,http-headers,http-methods,http-enum,http-robots.txt <TARGET_IP>
LOOKFOR: page title, `Server:` header, allowed methods (`PUT` is interesting), enumerated paths, robots entries.
DECISION: paths found → fetch them manually. `PUT` allowed → note it as a lead, do not upload yet.
NEXT: HTTP & HTTPS — Complete Command Reference for the full web workflow.
MISTAKE: `http-enum` is noisy and slow against large apps; it is a lead generator, not a directory brute-forcer.
EVIDENCE: titles and paths; they are often the fastest route into the app.

[nmap-14] 14. SMB family | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p139,445 --script smb-os-discovery,smb2-security-mode,smb-enum-shares,smb-enum-users <TARGET_IP>
LOOKFOR: hostname/domain/OS, `signing: enabled|disabled`, share names, account names.
DECISION: shares listed → go to SMB — Complete Command Reference. Signing disabled → relay becomes worth investigating (prerequisites still apply).
NEXT: SMB — Complete Command Reference Step 05.
MISTAKE: reading "signing disabled" as "relay will work". You still need a coercible authentication and a target that accepts the relayed identity.
EVIDENCE: the OS/domain block — it is often the first proof you are facing a domain-joined host.

[nmap-15] 15. FTP family | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p21 --script ftp-anon,ftp-syst,ftp-vsftpd-backdoor <TARGET_IP>
LOOKFOR: `Anonymous FTP login allowed`, server type/features, backdoor response.
DECISION: anonymous allowed → FTP — Complete Command Reference Step 06. Backdoor script positive → validate manually before any exploit.
NEXT: FTP — Complete Command Reference.
MISTAKE: firing a vsftpd exploit because the version is 2.3.4 — most 2.3.4 builds are not the backdoored one.
EVIDENCE: the version banner and the anonymous result.

[nmap-16] 16. DNS | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p53 --script dns-nsid,dns-zone-transfer --script-args dns-zone-transfer.domain=<DOMAIN> <TARGET_IP>
LOOKFOR: `zone-transfer:` records, or a transfer refusal.
DECISION: transfer succeeds → every hostname goes into `/etc/hosts` and gets probed. Refused → normal; brute-force instead.
NEXT: DNS — Complete Command Reference.
MISTAKE: running `dns-zone-transfer` without `--script-args` — the script has no domain to ask for.
EVIDENCE: the full zone dump, if you get one.

[nmap-17] 17. SSH | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p22 --script ssh-auth-methods,ssh2-enum-algos <TARGET_IP>
LOOKFOR: accepted auth methods; weak KEX/ciphers/host-key algorithms.
DECISION: `publickey` only + a key found on disk = worth trying. Password allowed → one careful attempt, not a brute force.
NEXT: SSH — Complete Command Reference.
MISTAKE: treating weak algorithms as an authentication bypass. They are not.
EVIDENCE: the auth-method line, before you attempt a login.

[nmap-18] 18. Database services | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
nmap -p3306 --script mysql-info <TARGET_IP>
nmap -p1433 --script ms-sql-info,ms-sql-ntlm-info <TARGET_IP>
LOOKFOR: protocol version, auth salt, instance name, NTLM domain/host info.
DECISION: MSSQL info leaks a domain name → useful for AD enumeration even before credentials.
NEXT: Database Services page (batch 2).
MISTAKE: `ms-sql-ntlm-info` needs the instance to answer pre-auth; silence is not a closed port.
EVIDENCE: instance and domain strings.

[nmap-19] 19. Broad vulnerability category | Advanced | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap --script vuln -p <TARGET_PORT> <TARGET_IP>
LOOKFOR: `VULNERABLE` blocks with CVE references.
DECISION: every hit is a lead, not a finding — reproduce manually before reporting or exploiting.
NEXT: validate, then exploit research.
MISTAKE: running this against fragile services on the exam; some scripts can crash a daemon and cost you the box.
EVIDENCE: the CVE IDs, with the manual reproduction that confirmed them.

[nmap-20] 20. Find the right script | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
ls /usr/share/nmap/scripts | grep -i <KEYWORD>
grep -l "categories" /usr/share/nmap/scripts/*.nse | head
LOOKFOR: a script name matching the service in front of you.
DECISION: no script → read the service's own documentation; NSE coverage is not exhaustive.
NEXT: run the script with `--script-help` first.
MISTAKE: guessing a script name. `--script-help` and the directory listing are authoritative.
EVIDENCE: the exact script name you used, so the scan is reproducible.

[nmap-21] 21. Save every format | Core | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -sCV -p <TARGET_PORT> -oA <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: three files appear: `.nmap` (readable), `.gnmap` (grep-able), `.xml` (machine-readable).
DECISION: use `.gnmap` for quick greps (`grep open *.gnmap`), `.xml` for reporting tools.
NEXT: Step 22 if you want an HTML appendix.
MISTAKE: using `-oN` everywhere and later having to re-scan for structured data.
EVIDENCE: all three files belong in `<OUTPUT_DIR>`.

[nmap-22] 22. Turn XML into an HTML appendix | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
xsltproc -o <OUTPUT_FILE>.html /usr/share/nmap/nmap.xsl <OUTPUT_FILE>.xml
LOOKFOR: a readable HTML file with the port table.
DECISION: useful for the report appendix; not required for scoring.
NEXT: attach or reference it in the report notes.
MISTAKE: passing the `.nmap` file instead of the `.xml`.
EVIDENCE: the HTML file plus the original XML.

[nmap-23] 23. Tune a slow or lossy scan | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
sudo nmap -p- -T3 --max-retries 2 --host-timeout 30m -oN <OUTPUT_FILE> <TARGET_IP>
LOOKFOR: fewer `no-response` ports and a stable completion.
DECISION: still missing ports → scan in ranges (`-p 1-10000`, `-p 10001-20000`) so a failure is contained.
NEXT: Step 06 on the confirmed list.
MISTAKE: raising `-T` to compensate for packet loss. It makes loss worse.
EVIDENCE: the timing options used — they explain why two scans differ.

[nmap-24] 24. Why aggressive timing lies | Core | Documented — Untested | runOn=kali | tags=nmap

[nmap-25] 25. Scan an internal host through SOCKS | Conditional | Syntax Checked | runOn=kali | tags=nmap
CMD(bash):
proxychains4 nmap -sT -Pn -n -p <TARGET_PORT> <TARGET_IP>
LOOKFOR: a result at all — proxied scans are slow and lossy.
DECISION: timeout → raise the proxy timeout and scan a single port; a whole-range scan through SOCKS is rarely worth it.
NEXT: once the port list is known, use the service's own client through the proxy.
MISTAKE: `-sS` through proxychains — SYN scans cannot traverse a SOCKS proxy; you must use `-sT`.
EVIDENCE: note that the result came via proxy; the report should say so. > **Pivoting variant (all pages):** if you are targeting an internal host, prepend `proxychains4` and add `-Pn` to skip host discovery, which usually fails through a proxy.

===== PAGE smb | SMB — Complete Command Reference =====

[smb-01] 01. Confirm SMB and grab the version | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nmap -sCV -p139,445 <TARGET_IP>
LOOKFOR: `microsoft-ds` on 445, `netbios-ssn` on 139, and a `VERSION` string with the host/domain.
DECISION: open → Step 02. 445 closed but 139 open → older stack; still worth enumerating.
NEXT: Step 02.
MISTAKE: stopping at "445 open" without a version — the version decides whether SMBv1 or a known CVE is even relevant.
EVIDENCE: the port table and version string.

[smb-02] 02. NSE SMB baseline | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nmap -p139,445 --script smb-os-discovery,smb-security-mode,smb2-security-mode,smb-enum-shares,smb-enum-users <TARGET_IP>
LOOKFOR: hostname, domain, OS build, `message_signing` state, share list, account list.
DECISION: shares listed → Step 05. `signing: disabled` → read section I before acting on it.
NEXT: Step 03 (null session) or Step 05.
MISTAKE: `smb-enum-users` needs a null session; an empty result usually means null sessions are off, not that there are no users.
EVIDENCE: the OS/domain block and the share list.

[smb-03] 03. Read the dialect and signing requirements | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nmap -p445 --script smb2-security-mode,smb2-capabilities <TARGET_IP>
LOOKFOR: `SMB2/3 message signing enabled but not required` vs `required`.
DECISION: "enabled but not required" = signing is optional → relay is *possible* in principle. "required" → relay to this host will fail.
NEXT: section I.
MISTAKE: equating "signing not required" with "relay will work". Feasibility still depends on a coerced authentication and on the relayed identity having access.
EVIDENCE: the exact signing line — quote it in the report.

[smb-04] 04. Force a protocol version when negotiation fails | Conditional | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbclient -L //<TARGET_IP>/ -N -m SMB3
smbclient -L //<TARGET_IP>/ -N --option='client min protocol=SMB2'
LOOKFOR: a share listing instead of `protocol negotiation failed`.
DECISION: SMB1-only host → `-m NT1` (lab only; SMB1 is a red flag worth reporting).
NEXT: Step 05.
MISTAKE: assuming a negotiation failure means the host is unreachable — it usually means the dialect is mismatched.
EVIDENCE: the dialect you had to force.

[smb-05] 05. Null session share listing | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbclient -N -L //<TARGET_IP>/
LOOKFOR: a `Sharename Type Comment` table including `IPC$`, `C$`, `ADMIN$`.
DECISION: `NT_STATUS_ACCESS_DENIED` → null sessions are disabled: move to credentialed enumeration. Listing works → Step 06.
NEXT: Step 06 (permissions) then Step 07.
MISTAKE: `-L` is the list flag and is case-sensitive; `-l` does not exist.
EVIDENCE: the share table.

[smb-06] 06. Permission map as null/guest | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbmap -H <TARGET_IP> -u '' -p ''
smbmap -H <TARGET_IP> -u guest -p ''
LOOKFOR: a `Disk`/`Permissions` table with `READ ONLY`, `READ, WRITE`, or `NO ACCESS`.
DECISION: any `READ` → Step 08. `READ, WRITE` → note it; uploading is a separate, authorised decision.
NEXT: Step 08.
MISTAKE: empty `-u ''` is a null attempt, not a guest login — try both. `NO ACCESS` on `C$` for a low-priv account is normal.
EVIDENCE: the per-share permission table.

[smb-07] 07. NetExec null/guest pass | Conditional | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nxc smb <TARGET_IP> -u '' -p '' --shares
LOOKFOR: `SMB` banner with host/domain, then share lines with `READ`/`WRITE`.
DECISION: `[+]` with guest → same path as Step 06. `STATUS_ACCESS_DENIED` → no anonymous access.
NEXT: Step 12 once you have credentials.
MISTAKE: NetExec is noisy in logs; it is fine in a lab, but it is not a stealth tool.
EVIDENCE: the banner is a quick source of hostname/domain strings.

[smb-08] 08. Recursive directory listing | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbmap -H <TARGET_IP> -u <USERNAME> -p <PASSWORD> -r <SHARE_NAME> --dir-only
LOOKFOR: an indented tree — backup folders, `IT`, `Finance`, user home directories, `*.bak`, `*.config`, scripts.
DECISION: a directory looks interesting → Step 09 to pull it, or Step 11 to grab one file.
NEXT: Step 09.
MISTAKE: **capital ****`-R`**** is not a valid smbmap flag.** The recursive flag is lowercase `-r`. `-R` fails with `unrecognized arguments: -R` (verified with `smbmap -h`; some course material prints it in uppercase).
EVIDENCE: the tree, saved with `-g` if you want a grep-able output file.

[smb-09] 09. List a specific subdirectory | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbmap -H <TARGET_IP> -u <USERNAME> -p <PASSWORD> -r '<SHARE_NAME>/<SUBDIR>'
LOOKFOR: file names, sizes, dates; recently modified files are usually the intended lead.
DECISION: readable files → Step 10 or 11. `NO ACCESS` on a subdirectory → try the parent or another account.
NEXT: Step 10 (bulk) or Step 11 (single file).
MISTAKE: quoting the path — spaces in share or directory names break the argument without single quotes.
EVIDENCE: the listing with timestamps.

[smb-10] 10. Interactive smbclient session | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbclient -N //<TARGET_IP>/<SHARE_NAME>
smbclient -U '<DOMAIN>/<USERNAME>%<PASSWORD>' //<TARGET_IP>/<SHARE_NAME>
LOOKFOR: `smb: \>` prompt, or `NT_STATUS_ACCESS_DENIED` / `NT_STATUS_BAD_NETWORK_NAME`.
DECISION: prompt appears → `ls`, `cd`, `recurse ON`, `prompt OFF`, `mget *`. Access denied → wrong account or wrong share name (case-insensitive but must exist).
NEXT: Step 11.
MISTAKE: using `//<TARGET_IP>\<SHARE_NAME>` — smbclient wants forward slashes in the UNC path.
EVIDENCE: a transcript of the listing you relied on.

[smb-11] 11. Non-interactive bulk download | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
mkdir -p <OUTPUT_DIR> && cd <OUTPUT_DIR>
smbclient -N //<TARGET_IP>/<SHARE_NAME> -c 'recurse ON; prompt OFF; mget *'
LOOKFOR: `getting file \path\file` lines, then files on disk.
DECISION: transfer errors on long paths → download subdirectories one at a time with `cd`/`mget`.
NEXT: Step 13 (inspect locally).
MISTAKE: running it from your home directory — you lose track of which box the files came from. Run inside `<OUTPUT_DIR>`.
EVIDENCE: the mirrored tree itself.

[smb-12] 12. Download one specific file | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbmap -H <TARGET_IP> -u <USERNAME> -p <PASSWORD> --download '<SHARE_NAME>/<PATH>/<FILE>'
smbclient -U '<DOMAIN>/<USERNAME>%<PASSWORD>' //<TARGET_IP>/<SHARE_NAME> -c 'get <FILE> <OUTPUT_FILE>'
LOOKFOR: the file appearing locally at the target path, or a `file not found` error.
DECISION: success → Step 13. Failure on a path that was listed → quote the path exactly; spaces need quoting.
NEXT: Step 13.
MISTAKE: downloading to a name that already exists — you silently overwrite earlier evidence.
EVIDENCE: the file plus its source path.

[smb-13] 13. Inspect what you pulled | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
find <OUTPUT_DIR> -type f -exec file {} +
grep -RIn -E 'pass|pwd|secret|token|key|connectionString' <OUTPUT_DIR>
LOOKFOR: config files, `.kdbx`, `.pfx`, scripts with hardcoded credentials, database backups, `unattend.xml`, `.ssh` directories.
DECISION: credentials found → validate them carefully (Step 14) and record where they came from. Nothing found → continue enumeration; not every share is the path.
NEXT: Step 14.
MISTAKE: grepping only for "password" — also try `pw`, `sa`, `uid=`, `user id=`, and base64-looking strings.
EVIDENCE: the file path plus the exact line containing the credential.

[smb-14] 14. Validate credentials and enumerate the domain in one pass | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nxc smb <TARGET_IP> -u <USERNAME> -p <PASSWORD> -d <DOMAIN> --shares --users --groups --loggedon-users --pass-pol
LOOKFOR: `[+]` auth success, share permissions, user list with `badpwdcount`, group memberships, active sessions, lockout policy.
DECISION: `(Pwn3d!)` → local admin, move to secrets dumping (Advanced). Valid but no admin → harvest more shares and BloodHound data.
NEXT: Step 15.
MISTAKE: running `--users` before reading `--pass-pol` — you may be two attempts from locking out every account.
EVIDENCE: the auth line (host + domain + user), the share table, the policy.

[smb-15] 15. Re-enumerate every share with the new identity | Core | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
smbmap -H <TARGET_IP> -u <USERNAME> -p <PASSWORD> -d <DOMAIN>
LOOKFOR: shares that were `NO ACCESS` before and are now readable — this is the single most common "new credential" win.
DECISION: new access → back to Step 09/11 with that share.
NEXT: Step 09.
MISTAKE: assuming your first enumeration was complete. Permissions are per-account; every new credential means re-running the basics.
EVIDENCE: the before/after permission difference.

[smb-16] 16. RPC enumeration | Conditional | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
rpcclient -U "" -N <TARGET_IP> -c "enumdomusers;enumdomgroups;querydominfo"
rpcclient -U '<DOMAIN>/<USERNAME>%<PASSWORD>' <TARGET_IP> -c "enumdomusers"

NEXT: password policy, then careful spraying.
MISTAKE: RID cycling (`impacket-lookupsid`) is noisy and often unnecessary once you have one credential.
EVIDENCE: the user/group list with RIDs.

[smb-20] 20. Build a relay candidate list | Advanced | Syntax Checked | runOn=kali | tags=smb
CMD(bash):
nxc smb <TARGET_IP>/24 --gen-relay-list <OUTPUT_FILE>
LOOKFOR: hosts where signing is not required, one IP per line.

===== PAGE ftp | FTP — Complete Command Reference =====

[ftp-01] 01. Confirm the service and version | Core | Syntax Checked | runOn=kali | tags=ftp
CMD(bash):

===== PAGE ssh | SSH — Complete Command Reference =====

[ssh-01] 01. Confirm the service and version | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
nmap -sV -p22 <TARGET_IP>
PURPOSE: prove SSH is listening and capture the server implementation/version before choosing an authentication path.
PREREQS: target reachable from Kali; authorised scope confirmed.
LOOKFOR: `22/tcp open ssh` and an `OpenSSH version` banner. If the port is closed or filtered, that is a result, not a failure.
SUCCESS: port open with an SSH banner → continue to Step 02. A non-standard port is fine if the banner identifies SSH; rerun detection with `-p <TARGET_PORT>`.
FAILURE: closed or filtered → check the port scan and other open services. Do not run authentication tests against a port with no SSH service. If the host is unreachable, fix routing/VPN first.
DECISION: SSH open → establish authentication behavior next. SSH closed → leave the SSH branch and investigate the services that are actually exposed.
NEXT: Step 02.
MISTAKE: assuming an unusual port means “not SSH”; confirm the banner on every unknown port instead.
EVIDENCE: port state, service name and version.

[ssh-02] 02. Ask without authenticating | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh -o PreferredAuthentications=none -o StrictHostKeyChecking=no <USERNAME>@<TARGET_IP>
CMD(bash):
nmap -p22 --script ssh-auth-methods <TARGET_IP>
PURPOSE: ask the server which authentication methods it will offer without supplying a password or key.
PREREQS: SSH confirmed open; a candidate username, even if unverified.
LOOKFOR: a `Permission denied (publickey,password).` line, or a similar list of methods. The methods shown are the useful result. The Nmap script can provide a second view; neither output is a guaranteed complete list.
SUCCESS: `publickey` appears → prioritize key discovery (Step 06). `password` appears → test a known credential (Step 05) before considering any guessing. Both appear → use the credential/key you already have first.
FAILURE: no method list, timeout, or connection failure → go to Step 04 for diagnostics. The server may also vary its response by user or configuration, so do not treat one response as a complete inventory.
DECISION: a usable credential or key source decides the branch. Do not start password guessing just because `password` is listed.
NEXT: Step 05 if a known credential exists; Step 06 if keys are the likely path; Step 04 if the response is unclear.
MISTAKE: using `ssh -v` for this and reading a wall of debug output; `PreferredAuthentications=none` answers the method question directly.
EVIDENCE: the exact method list, username and timestamp.

[ssh-10] 03. Read the algorithm list | Conditional | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
nmap -p22 --script ssh2-enum-algos <TARGET_IP>
PURPOSE: record the server’s key-exchange, host-key, cipher and MAC algorithms while the connection is still unauthenticated, so later negotiation failures have evidence.
PREREQS: SSH confirmed open; Nmap SSH scripts installed.
LOOKFOR: KEX algorithms, host-key algorithms, encryption ciphers and MACs. Note anything legacy such as `diffie-hellman-group1-sha1`, `ssh-rsa`, `arcfour` or `3des-cbc`.
SUCCESS: algorithms recorded → use them only if a later connection fails during negotiation. Use the compatibility subsection (Step 12) with the smallest matching option.
FAILURE: script returns nothing or errors → verify the Nmap script path and rerun with `--script-trace` if needed. Do not infer supported algorithms from a failed script.
DECISION: legacy algorithms are a hardening finding, not an authentication bypass. They do not grant access and should not be reported as one.
NEXT: Step 04 if diagnostics are needed; otherwise Step 05 or Step 06.
MISTAKE: reporting “weak SSH algorithms” as if it is an access path; it is a configuration observation.
EVIDENCE: the full algorithm list and the exact Nmap command.

[ssh-03] 04. Verbose connection trace | Conditional | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh -v <USERNAME>@<TARGET_IP>
PURPOSE: see where the connection stops when detection or authentication behavior is inconclusive.
PREREQS: a candidate username; the failure has already been observed once.
LOOKFOR: protocol negotiation, host-key type, `Authentications that can continue:`, and the last successful stage before failure.
SUCCESS: an authentication list appears → return to Step 02/05 and choose the matching credential path. A clean handshake that reaches authentication is normal.
FAILURE: failure before authentication → network, host-key or algorithm problem; use Step 03 results and Step 13. Failure after authentication starts → check the credential, username and key.
DECISION: use higher verbosity only when it answers a specific question. A timeout is not an algorithm error; diagnose reachability first.
NEXT: Step 05 or Step 06 when authentication is reached; Step 03/12 only for a demonstrated negotiation mismatch.
MISTAKE: leaving the command running while it waits for a password; use `Ctrl-C` and rerun with a non-interactive option only when appropriate.
EVIDENCE: the algorithm, auth-method and failure lines, with secrets removed.

[ssh-04] 05. One deliberate attempt, not a brute force | Conditional | Documented — Untested | runOn=kali | tags=ssh
CMD(bash):
sshpass -p '<PASSWORD>' ssh -o StrictHostKeyChecking=no <USERNAME>@<TARGET_IP>
PURPOSE: test a credential discovered through authorised enumeration exactly once, without turning SSH into a noisy password-guessing exercise.
PREREQS: a known username and password from an authorised source; password authentication appears available; lab rules permit credential use.
LOOKFOR: a shell prompt, or `Permission denied`.
SUCCESS: shell obtained → record the exact command and host-key fingerprint, then enumerate the host and move to the privilege-escalation page.
FAILURE: denied → confirm the username, the authentication method and the credential source before trying anything else. Check SMB/HTTP shares, configs and notes for a better credential. Do not loop over a wordlist.
DECISION: `sshpass` is a non-interactive password-passing utility, not inherently a brute-force tool. Keep a known-credential attempt distinct from password spraying or guessing.
NEXT: Step 06 for keys or a better credential source. Use password guessing only if the lab rules explicitly allow it and the noise is acceptable.
MISTAKE: spraying SSH before checking other services for credentials; the password is often already on the target.
EVIDENCE: success banner, username, host-key fingerprint and timestamp. Never put the password in shared notes.

[ssh-05] 06. Identify a found key | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
file <KEY_FILE>
head -1 <KEY_FILE>
ssh-keygen -y -f <KEY_FILE>
PURPOSE: determine whether the file is a usable private key, which format it uses, and whether it is encrypted.
PREREQS: a candidate key copied from an authorised location.
LOOKFOR: `OpenSSH private key` versus `PEM RSA private key`; the first line of the file; `ssh-keygen -y` printing the matching public key, or prompting for a passphrase.
SUCCESS: public key prints → the key is unencrypted and structurally readable; continue to Step 07 to check authorisation, then Step 08 for permissions.
FAILURE: `invalid format` → check whether the file is a public key, a certificate, a partial download or a different format. A passphrase prompt is not a failure; go to Step 09 after permissions. Do not assume a key is authorised merely because it parses.
DECISION: format is readable → validate fingerprint and permissions before use. Format is unreadable → repair or obtain a complete copy before trying to connect.
NEXT: Step 07.
MISTAKE: treating a public key or an `authorized_keys` line as a private key; only a private key can authenticate a client.
EVIDENCE: key type, first-line header and the derived public-key fingerprint. Never record private key material in a shared page.

[ssh-06] 07. Check matching public keys | Conditional | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh-keygen -lf <KEY_FILE>          # fingerprint
ssh-keygen -lf ~/.ssh/authorized_keys
PURPOSE: compare the found key’s fingerprint with keys that are actually authorised for the target account.
PREREQS: a readable key; an `authorized_keys` file or equivalent evidence from the target.
LOOKFOR: the same fingerprint on both sides. A matching fingerprint identifies the key; a matching `authorized_keys` entry is what suggests authorisation.
SUCCESS: fingerprint matches a target account’s authorised key → continue to Step 08 and prepare permissions.
FAILURE: no match → the key is not authorised for that account, or you are looking at the wrong user/source. Check other accounts and key locations; do not assume the key will work.
DECISION: fingerprinting proves identity/format, not successful authentication. Keep the distinction in notes and reports.
NEXT: Step 08 after a plausible match; otherwise return to Step 06/key discovery.
MISTAKE: comparing key text by eye instead of comparing fingerprints.
EVIDENCE: the fingerprint pair, the account and the source path.

[ssh-07] 08. Fix permissions before SSH refuses the key | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
chmod 600 <KEY_FILE>
PURPOSE: satisfy OpenSSH’s common private-key permission requirement before attempting authentication.
PREREQS: the key has been validated and copied to a local working path.
LOOKFOR: no output; `ls -l <KEY_FILE>` shows `-rw-------`.
SUCCESS: permissions corrected → continue to Step 09 (passphrase check) or Step 11 if the key is already known to be unencrypted and authorised.
FAILURE: permission change fails → check ownership, path and whether the key lives on a read-only/mounted share. Copy it to `<OUTPUT_DIR>` and retry.
DECISION: restrictive permissions are commonly required for private keys; do not change public-key permissions unnecessarily.
NEXT: Step 09.
MISTAKE: editing or using a key directly from a mounted share; copy it locally first.
EVIDENCE: `ls -l <KEY_FILE>` showing mode `-rw-------`.

[ssh-08] 09. Detect the passphrase | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh-keygen -y -f <KEY_FILE>
PURPOSE: determine whether the private key is encrypted before deciding whether recovery is needed.
PREREQS: validated key and restrictive permissions in place.
LOOKFOR: `Enter passphrase:` → encrypted; a printed `ssh-rsa AAAA...` or equivalent public key → not encrypted.
SUCCESS: unencrypted → go to Step 11 and connect. Encrypted with a usable passphrase → go to Step 11 and enter it when prompted.
FAILURE: encrypted and passphrase unavailable → continue to Step 10, but only in an authorised environment. If the file cannot be parsed, return to Step 06.
DECISION: do not crack a key unless recovery is authorised and the passphrase is actually missing.
NEXT: Step 11 if usable; Step 10 if recovery is justified.
MISTAKE: assuming an encrypted key is unusable; it may be usable with a known passphrase, and it is not the same thing as a login password.
EVIDENCE: whether a passphrase is required, and whether a usable passphrase is already available. Do not record the passphrase itself.

[ssh-09] 10. Crack the passphrase | Conditional | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh2john <KEY_FILE> > <OUTPUT_FILE>

john --show <OUTPUT_FILE>
PURPOSE: recover a missing passphrase for an encrypted private key when the lab rules allow it.
PREREQS: encrypted key; `ssh2john` and John installed; an authorised wordlist and environment.
LOOKFOR: a recovered passphrase in the John output, or a failed/exhausted run.
SUCCESS: passphrase recovered → use it with Step 11. Prefer an interactive prompt or a local agent; do not place the passphrase in a shared page.
FAILURE: not recovered → try a targeted wordlist once, then return to alternative credentials or enumeration. Recovery is optional, not mandatory.
DECISION: distinguish an encrypted key’s passphrase from a normal login password. Only recover in an authorised environment.
NEXT: Step 11 with the recovered passphrase, or an alternative access path.
MISTAKE: piping the key into older `ssh2john` versions or forgetting the output file that John needs.
EVIDENCE: the John mode, wordlist and success/failure result; store any recovered secret only in the private machine notes.

[ssh-12] 11. Connect using the private key | Core | Syntax Checked | runOn=kali | tags=ssh
CMD(bash):
ssh -i <KEY_FILE> <USERNAME>@<TARGET_IP>
PURPOSE: authenticate with the validated private key and obtain a shell.
PREREQS: key format checked; fingerprint/authorisation plausibly established; permissions set to `600`; passphrase known or key unencrypted.
LOOKFOR: a host-key verification prompt followed by a shell prompt. Verify the host-key fingerprint against independent evidence where the lab requires it.
SUCCESS: shell obtained → record the exact command and host-key fingerprint, then enumerate the host and move to the privilege-escalation page.
FAILURE: `Permission denied (publickey)` → the key is not authorised for that user/account; recheck the username and `authorized_keys`. `Load key... invalid format` → return to Step 06. `Permissions... too open` → return to Step 08. A negotiation error → use Step 03 and the targeted compatibility subsection (Step 12). A timeout → go to Step 13 and diagnose reachability instead of changing algorithms.
DECISION: success confirms the key/account pair, not that every account accepts the key. Failure should route to the specific cause above, not to random option changes.
NEXT: enumerate the shell; then use [Linux Privilege Escalation — Complete Command Reference](#/p/linux-privesc) for the local privilege-escalation workflow.
MISTAKE: using the wrong username, forgetting `-i`, or assuming a key is authorised before checking the target’s `authorized_keys`.
EVIDENCE: the exact `ssh` command, username, host-key fingerprint and initial shell identity (`id`/hostname).

[ssh-11] 12. Connect with legacy algorithms when required | Advanced | Documented — Untested | runOn=kali | tags=ssh
CMD(bash):
ssh -oKexAlgorithms=+diffie-hellman-group1-sha1 -oHostKeyAlgorithms=+ssh-rsa -oPubkeyAcceptedAlgorithms=+ssh-rsa <USERNAME>@<TARGET_IP>
PURPOSE: provide a narrowly scoped compatibility path when evidence shows the server rejects the modern negotiation set.
PREREQS: Step 03 algorithm output and Step 04 negotiation evidence showing a specific mismatch; a normal connection has already failed for that reason.
LOOKFOR: a successful handshake where the default client refused. If the failure is authentication, timeout or a permission error, this step is the wrong tool.
SUCCESS: connection succeeds → use the session normally and record exactly which options were required.
FAILURE: still fails → inspect the specific KEX, host-key, cipher or MAC mismatch and add only the required option. Do not enable a blanket weak-algorithm profile.
DECISION: use this only when the error is a negotiation error such as `no matching host key type found` or `no matching key exchange method found`. Do not apply an algorithm workaround to auth or connectivity failures.
NEXT: use the session normally, then report the legacy requirement as a configuration finding.
MISTAKE: enabling weak algorithms globally or leaving them in aliases/history for later targets; use a one-off command.
EVIDENCE: the exact forced options and the server/client negotiation lines.

[tunneling-01] 01. Local port forward (ssh -L) | Core | Syntax Checked | runOn=kali | tags=pivoting
CMD(bash):

LOOKFOR: a normal SSH session; while it stays open, `127.0.0.1:<LOCAL_PORT>` on Kali reaches `<REMOTE_PORT>` **as seen from the pivot**.
DECISION: the service is on another internal host → point the middle at that host: `ssh -L <LOCAL_PORT>:<INTERNAL_IP>:<REMOTE_PORT> <USERNAME>@<TARGET_IP>`.
NEXT: connect to `127.0.0.1:<LOCAL_PORT>` on Kali.
MISTAKE: assuming the forward reaches Kali's network. The right-hand side is resolved **from the pivot**, not from Kali.
EVIDENCE: the SSH session plus a successful connection to the forwarded port.

[tunneling-02] 02. Remote port forward (ssh -R) | Core | Syntax Checked | runOn=kali | tags=pivoting

# example: make Kali's HTTP server reachable on the target network

LOOKFOR: traffic to `<TARGET_IP>:<REMOTE_PORT>` arriving at Kali's `127.0.0.1:<LOCAL_PORT>`.
DECISION: internal hosts must reach your payload server → this is the pattern (serve from Kali, forward onto the pivot).

MISTAKE: `GatewayPorts no` (the default) binds the remote listener to `127.0.0.1` on the pivot — only the pivot itself can use it. Add `-R 0.0.0.0:<REMOTE_PORT>:…` only if the server allows it.
EVIDENCE: a `curl` from the pivot to `127.0.0.1:<REMOTE_PORT>`.

===== PAGE exam-execution | Exam Execution & Reporting — Proof, Timeline and Submission =====

[exam-execution-01] 01. Create the workspace | Core | Syntax Checked | runOn=kali | tags=exam
CMD(bash):
mkdir -p ~/exam/{scans,loot,screens,notes}
ls -la ~/exam
LOOKFOR: four directories, created once, at the start.
DECISION: every artefact goes into one of them — scans by host, loot by host, screenshots by sequence, notes by host.
NEXT: Step 02.
MISTAKE: saving evidence to `~/Downloads` or `/tmp`. Files there get lost on reboot or collided between hosts.
EVIDENCE: the directory listing.

[exam-execution-02] 02. Naming discipline | Core | Syntax Checked | runOn=kali | tags=exam
CMD(bash):
mkdir -p ~/exam/scans/<TARGET_IP> ~/exam/loot/<TARGET_IP>
# scans: ~/exam/scans/<TARGET_IP>/nmap_full.txt
# loot:  ~/exam/loot/<TARGET_IP>/<SERVICE>_<WHAT>.txt
# shots: ~/exam/screens/<TARGET_IP>_<STEP>_<WHAT>.png
LOOKFOR: a path you can reconstruct a week later.
DECISION: host-first naming (`<IP>__`) sorts correctly and survives copy/paste into the report.
NEXT: Step 03.
MISTAKE: `screenshot1.png`. Twenty of those and you cannot tell which host or which privilege level it proves.
EVIDENCE: the naming scheme in use.

[exam-execution-03] 03. Linux host proof | Core | Syntax Checked | runOn=either | tags=exam
CMD(bash):
whoami; hostname; ip a; cat /etc/hostname
cat /root/local.txt
cat /root/proof.txt
LOOKFOR: the flag contents, plus hostname/IP visible **in the same terminal**.
DECISION: `local.txt` proves user, `proof.txt` proves root — capture both at the moment you obtain them.
NEXT: screenshot immediately (Step 06).
MISTAKE: capturing the flag, then closing the shell, then having no proof of **which** host it came from.
EVIDENCE: one screen showing the command, the flag, and `ip a`/`hostname`.

[exam-execution-04] 04. Windows host proof | Core | Syntax Checked | runOn=windows | tags=exam
CMD(bash):
whoami; hostname; ipconfig
type C:\Users\<USERNAME>\Desktop\local.txt
type C:\Users\Administrator\Desktop\proof.txt
LOOKFOR: `nt authority\system` or the Administrator context, the hostname, the IPv4 address, and the flag.
DECISION: Administrator vs SYSTEM matters for the write-up — state which account you used.
NEXT: screenshot (Step 06).
MISTAKE: running `type` in a different session from `whoami`. The grader must see them together.
EVIDENCE: the combined output in one screenshot.

[exam-execution-05] 05. Read local and proof files | Core | Syntax Checked | runOn=either | tags=exam
CMD(bash):
cat /root/proof.txt 2>/dev/null; type C:\Users\Administrator\Desktop\proof.txt 2>nul
LOOKFOR: the correct file for the privilege level you reached.
DECISION: `local.txt` without `proof.txt` means the box is half-done — do not move on and forget it.
NEXT: continue escalation, then recapture.
MISTAKE: copying the flag into notes without a screenshot. Notes are supporting evidence; the screenshot is the proof.
EVIDENCE: the file path and the flag value.

[exam-execution-06] 06. Screenshot with a naming scheme | Core | Documented — Untested | runOn=kali | tags=exam
CMD(bash):
scrot -s ~/exam/screens/$(date +%H%M%S)_proof.png
# alternative, if scrot is unavailable: use the hypervisor/VM screenshot tool
LOOKFOR: a PNG that includes the flag **and** the host identity.
DECISION: `scrot` is not installed on this host — install it on your own exam VM, or use the VM console's screenshot function. Test the chosen method **before** exam day.
NEXT: Step 11 (hash it).
MISTAKE: cropping the screenshot so the hostname/IP disappears. Never crop the terminal header.
EVIDENCE: the PNG file itself, named with host and purpose.

[exam-execution-07] 07. The one-image rule | Core | Documented — Untested | runOn=either | tags=exam
LOOKFOR: no ambiguity about which machine the flag belongs to.
DECISION: you cannot prove host identity → the flag is worth nothing in a dispute. Recapture.
NEXT: hash and file it.
MISTAKE: proving root access with a screenshot of `id` only. That shows a privilege level, not a completed box.
EVIDENCE: the paired images, sequentially numbered.

[exam-execution-08] 08. Timestamp your activity | Core | Syntax Checked | runOn=kali | tags=exam
CMD(bash):
date -u; date +%H:%M:%S >> ~/exam/notes/timeline.txt
LOOKFOR: a monotonic log of what you did and when.
DECISION: useful when the report needs "initial access at …", and when you must explain a gap.
NEXT: append a one-line entry at each major milestone.
MISTAKE: writing the timeline at the end from memory. It will be wrong, and it reads like it.
EVIDENCE: `~/exam/notes/timeline.txt`.

[exam-execution-09] 09. Per-machine notes | Core | Syntax Checked | runOn=kali | tags=exam
LOOKFOR: enough detail that you could redo the box from the notes alone.
DECISION: if a step produced a credential or a shell, it belongs in the notes **and** in the final report.
NEXT: Step 10.
MISTAKE: notes that record only the final command. The report needs the path, including failed branches that explain your choices.
EVIDENCE: one note file per host.

[exam-execution-10] 10. Time budget | Core | Documented — Untested | runOn=other | tags=exam
LOOKFOR: a box that has consumed its budget without a foothold.
DECISION: park it, take the easy points elsewhere, come back with fresh eyes.
NEXT: move to the next target and log the switch in the timeline.
MISTAKE: sinking 8 hours into one machine while three others remain untouched.
EVIDENCE: the budget vs actual, in the timeline.

[exam-execution-11] 11. Hash the evidence | Core | Syntax Checked | runOn=kali | tags=exam
CMD(bash):
md5sum ~/exam/screens/*.png ~/exam/loot/* 2>/dev/null
sha256sum ~/exam/screens/*.png
LOOKFOR: a hash list you can re-verify before upload.
DECISION: hashes differ after copying → the copy corrupted (rare); re-copy before submitting.
NEXT: keep the hash file with the report.
MISTAKE: hashing an empty glob (no files matched) and calling it verified. Check the file count first.
EVIDENCE: the hash list and the matching files.

[exam-execution-12] 12. Revert a broken target | Conditional | Documented — Untested | runOn=other | tags=exam
LOOKFOR: the documented revert control in the exam environment — not a guess at `vmrun` or a hypervisor CLI.
DECISION: the box is unstable or credentials are bricked → revert, then redo only the steps needed to regain your position.
NEXT: re-capture proof if the revert lost it.
MISTAKE: reverting after you already captured the flag and losing the shell state — capture and hash proof **before** any revert.
EVIDENCE: the timeline entry for the revert and the reason.

===== PAGE troubleshooting | Troubleshooting — Complete Command Reference =====

[troubleshooting-01] 01. Check the local stack and route | Core | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
ip a; ip route; ping -c 3 <TARGET_IP>
ip route get <TARGET_IP>
LOOKFOR: an address on the correct interface, a default route, and ICMP replies.
DECISION: no reply but the route exists → ICMP may be filtered; continue to Step 03 (TCP). Wrong interface/route → fix VPN/routing before anything else.
NEXT: Step 02.
MISTAKE: treating a failed `ping` as "host down". Many exam targets drop ICMP while serving TCP perfectly.
EVIDENCE: the `ip a`/`ip route` output and the ping result.

[troubleshooting-02] 02. Check DNS | Core | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
cat /etc/resolv.conf
dig +short <DOMAIN>
getent hosts <DOMAIN>
LOOKFOR: the intended resolver, the expected A record, and `getent` agreeing with `dig`.
DECISION: `dig` works but an application fails → the app uses `/etc/hosts` or a different resolver. Add the entry explicitly.
NEXT: Step 03.
MISTAKE: debugging DNS when you should use the IP. If the record is wrong, put the mapping in `/etc/hosts` and move on.
EVIDENCE: the resolver config and the resolved address.

[troubleshooting-03] 03. Raw TCP probe | Core | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
nc -nv <TARGET_IP> <TARGET_PORT>
# scriptable
nc -z -v <TARGET_IP> <TARGET_PORT> && echo OPEN || echo CLOSED
LOOKFOR: `succeeded` / `open`, or a banner.
DECISION: open but the exploit fails → the service is there; the problem is protocol/credentials. Closed/timeout → firewall or wrong port.
NEXT: Step 04 (if you expect a listener) or Step 05 (HTTP).
MISTAKE: testing through proxychains when the tool uses UDP, or forgetting that `-z` sends no payload and some services log it.
EVIDENCE: the probe result.

[troubleshooting-04] 04. See what is listening locally | Core | Syntax Checked | runOn=either | tags=troubleshooting
CMD(bash):
ss -tlnp
ss -tulpn
LOOKFOR: the port bound to `0.0.0.0` vs `127.0.0.1`.
DECISION: bound to `127.0.0.1` → only local processes can reach it; tunnel in (Tunneling page). Not listening → the service is down.
NEXT: Step 05 or the pivot.
MISTAKE: starting a listener on `127.0.0.1` and expecting a remote callback. Bind `0.0.0.0` or the correct interface.
EVIDENCE: the `ss` line for the port.

[troubleshooting-05] 05. Verbose HTTP | Core | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
curl -v http://<TARGET_IP>:<TARGET_PORT>/
curl -vk https://<TARGET_IP>:<TARGET_PORT>/
curl -v --resolve <DOMAIN>:<TARGET_PORT>:<TARGET_IP> https://<DOMAIN>:<TARGET_PORT>/
LOOKFOR: `Connected to …`, the request line, response headers, and the status code.
DECISION: HTTP works but the browser/app does not → vhost or Host header. TLS handshake fails → `-k` or SNI (use `--resolve`).
NEXT: the HTTP or Directory & VHost page.
MISTAKE: reading only the body. `-v` shows the redirect, the auth challenge, and the exact header causing the failure.
EVIDENCE: the `-v` transcript.

[troubleshooting-06] 06. Capture traffic | Conditional | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
sudo tcpdump -i <INTERFACE> -nn -A port <TARGET_PORT>
sudo tcpdump -i <INTERFACE> -nn -w <OUTPUT_FILE> host <TARGET_IP>
LOOKFOR: whether packets leave, and whether anything returns.
DECISION: SYN out, nothing back → filtered/routed wrong. SYN, RST → port closed. SYN, SYN-ACK, then RST → TLS/app mismatch. Nothing at all → wrong interface.
NEXT: fix the layer the capture proves is broken.
MISTAKE: capturing on `eth0` while the traffic uses `tun0`. Confirm with `ip route get <TARGET_IP>`.
EVIDENCE: the pcap file, or the filtered output showing the handshake.

[troubleshooting-07] 07. Read the failure correctly | Core | Syntax Checked | runOn=kali | tags=troubleshooting
MISTAKE: jumping to the exploit when the handshake already shows the port is closed. Read the four packets first.

[troubleshooting-08] 08. Verify the path through a proxy | Conditional | Syntax Checked | runOn=kali | tags=troubleshooting
CMD(bash):
proxychains4 -q curl -v http://<INTERNAL_IP>/
proxychains4 -q nc -nv <INTERNAL_IP> <TARGET_PORT>
nmap -Pn -sT -p <TARGET_PORT> <INTERNAL_IP>
LOOKFOR: responses that only appear when the proxy is in use.
DECISION: `curl` fails but `nc` works → application issue, not routing. Both fail → the pivot cannot reach the target; test from the pivot itself.
NEXT: fix the tunnel (Tunneling & Pivoting).
MISTAKE: using `-sS` or ICMP through a SOCKS proxy. Use `-sT -Pn`.
EVIDENCE: the proxied transcript.
