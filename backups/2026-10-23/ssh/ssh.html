Prefer ProxyJump: ssh -J @ @ — one session, no SOCKS layer, and the resulting shell can still forward ports with -L. ## 1. Detect SSH ### Step 01 — Confirm the service and version Priority: Core · Run on: Kali · Status: Syntax Checked ```bash nmap -sCV -p22 --script ssh-auth-methods,ssh2-enum-algos ``` Look for: OpenSSH , the accepted auth methods, and the KEX/host-key algorithms.
Decision: publickey only → hunt for keys (Step 04). password allowed → Step 03, carefully.
Next: Step 02.
Common mistake: assuming an unusual port means "not SSH" — check the banner on every unknown port.
Evidence: the version and the auth-methods line. ## 2. Authentication-method discovery ### Step 02 — Ask without authenticating Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh -o PreferredAuthentications=none -o StrictHostKeyChecking=no @ ``` Look for: Permission denied (publickey,password). — the list is the answer.
Decision: the methods shown decide your next move; nothing is attempted yet.
Next: Step 03 or Step 04.
Common mistake: using ssh -v for this and reading a wall of debug output — the PreferredAuthentications=none form answers the question in one line.
Evidence: the exact method list. ### Step 03 — Verbose connection trace Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash ssh -v @ ``` Look for: Authentications that can continue:, server host key type, and where the handshake stops.
Decision: handshake fails before auth → algorithm or network problem (Step 07/08). Auth list shown → normal.
Next: Step 03 (credentials) or Step 04 (keys).
Common mistake: leaving it running — it will prompt for a password; Ctrl-C.
Evidence: the algorithm and auth-method lines. ## 3. Credential testing (careful) ### Step 04 — One deliberate attempt, not a brute force Priority: Conditional · Run on: Kali · Status: Documented — Untested ```bash sshpass -p '' ssh -o StrictHostKeyChecking=no @ ``` Look for: a shell, or Permission denied.
Decision: denied → stop. Do not loop over a wordlist: SSH is slow and noisy, and repeated failures may be logged or blocked.
Next: find a better credential source (shares, configs, notes).
Common mistake: spraying SSH before checking SMB/HTTP for credentials; the password is usually already on the box.
Evidence: the success banner and host key fingerprint. ## 4. Key identification and inspection ### Step 05 — Identify a found key Priority: Core · Run on: Kali · Status: Syntax Checked ```bash file head -1 ssh-keygen -y -f ``` Look for: OpenSSH private key vs PEM RSA private key; ssh-keygen -y printing the public key (and prompting for a passphrase if encrypted).
Decision: passphrase prompt → Step 07. Public key prints → the key is usable as-is.
Next: Step 06.
Common mistake: a -----BEGIN OPENSSH PRIVATE KEY----- key in an old tool that only understands PEM — convert with ssh-keygen -p -m PEM -f .
Evidence: the key type and fingerprint (ssh-keygen -lf .pub). ### Step 06 — Check matching public keys Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash ssh-keygen -lf # fingerprint ssh-keygen -lf ~/.ssh/authorized_keys ``` Look for: the same fingerprint on both sides.
Decision: fingerprint matches a user's authorized_keys (found in a share or web root) → that key logs in as that user.
Next: ssh -i @.
Common mistake: comparing key text by eye; fingerprints are the reliable comparison.
Evidence: the fingerprint pair. ## 5. Key permissions ### Step 07 — Fix permissions before SSH refuses the key Priority: Core · Run on: Kali · Status: Syntax Checked ```bash chmod 600 ``` Look for: no output; the Permissions 0644 ... are too open warning disappears.
Decision: warning persists → check ownership too (ls -l).
Next: ssh -i @.
Common mistake: editing the key inside a mounted share — copy it to first, then chmod.
Evidence: ls -l showing mode -rw-------. ## 6. Passphrase-protected keys ### Step 08 — Detect the passphrase Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh-keygen -y -f ``` Look for: Enter passphrase: → encrypted; a printed ssh-rsa AAAA... → not encrypted.
Decision: encrypted → Step 09.
Next: Step 09.
Common mistake: assuming an encrypted key is unusable — it is crackable if the passphrase is weak.
Evidence: whether a passphrase is required. ### Step 09 — Crack the passphrase Priority: Core · Run on: Kali · Status: Syntax Checked ```bash ssh2john > john --wordlist= john --show ``` Look for: :.
Decision: cracked → ssh -i and enter it. Not cracked → try a targeted wordlist; do not burn the clock.
Next: log in, then enumerate.
Common mistake: ssh2john needs the file path, not piped stdin in older versions — and the output must go to a file for john.
Evidence: the cracked passphrase (store it in the machine notes, not in a shared page). ## 7. Weak or legacy algorithms ### Step 10 — Read the algorithm list Priority: Conditional · Run on: Kali · Status: Syntax Checked ```bash nmap -p22 --script ssh2-enum-algos ``` Look for: diffie-hellman-group1-sha1, ssh-rsa, arcfour, 3des-cbc.
Decision: legacy algorithms are a hardening finding, not an authentication bypass. They may matter for an old client or a MITM scenario, nothing more.
Next: Step 11 only if you actually need to connect with a legacy client.
Common mistake: reporting "weak SSH algorithms" as if it grants access. It does not.
Evidence: the algorithm list, labelled as a configuration observation. ### Step 11 — Connect with legacy algorithms when required Priority: Advanced · Run on: Kali · Status: Documented — Untested ```bash ssh -oKexAlgorithms=+diffie-hellman-group1-sha1 -oHostKeyAlgorithms=+ssh-rsa -oPubkeyAcceptedAlgorithms=+ssh-rsa @ ``` Look for: a successful handshake where the default client refused.
Decision: still fails → the server may require an even older cipher (-c 3des-cbc).
Next: use the session normally.
Common mistake: leaving these options in your shell history for later targets — they weaken every future connection.
Evidence: the forced options, so the result is reproducible. ## 8. Troubleshooting | Symptom | Cause | Fix | | --- | --- | --- | | Connection refused | Nothing listening, or wrong port | Confirm the port scan | | Connection timed out | Firewall | Try through a pivot | | Permission denied (publickey) | No matching key | Find the key, or another user | | Too many authentication failures | Agent offering every key | -o IdentitiesOnly=yes -i | | REMOTE HOST IDENTIFICATION HAS CHANGED | Rebuilt host, new key | ssh-keygen -R | | no matching host key type found | Client too new for server | Step 11 | | Permissions 0644 ... are too open | Key mode | chmod 600 | | Load key ... invalid format | PEM vs OpenSSH | ssh-keygen -p -m PEM -f | Stop condition: no credentials, no keys, and password auth denied → SSH is not the entry point. Re-check shares and web roots for a key before giving up. ## 9. Quick workflow 1. nmap -sCV -p22 --script ssh-auth-methods,ssh2-enum-algos. 2. ssh -o PreferredAuthentications=none @ — methods. 3. Search shares/web roots for keys and credentials. 4. file + ssh-keygen -y -f the key. 5. chmod 600. 6. Encrypted → ssh2john + john. 7. ssh -i @. 8. Enumerate from the new shell; then go to the privesc page. ## 10.
